# Changelog

All notable changes to OpenLens are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and OpenLens uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Before 1.0.0, a minor version (0.x.0) may change behaviour; each such change is listed under **Changed**. A change that asks for action starts with **Breaking:** and follows the [stability policy](docs/stability.md).

## [Unreleased]

### Added

- **One visitor from the landing page to the app** (#710, D-102): `GET /flags` lists the project's sister hosts (the exact hosts its host rules map to the page's environment, at most 20). When an anonymous visitor follows a link to one of them, the browser SDK adds the anonymous id to that link (`_ol=<id>`, at the click only); the SDK on the other host adopts it when it has no history of that visitor, then removes it from the address bar. No cookie, never in cookieless mode or without consent; a single-host app sees no change.
- **`verify` checks that a visit is linked to the person** (#711): `openlens-cli verify` (and the MCP `verify`) sends a test anonymous page view and an `$identify` linking it (a test person marked internal, in `development`), waits up to 45 s for the page view to belong to the person, and reports `visitor linked to the person`, saying when the project has a single production host. It does not change `ok`. The wiring guide gains a *Landing page and app* section: one project key on both, host rules naming both hosts, `identify` right after account creation with `created_at`.

### Changed

- **A referrer on one of the project's hosts is `internal`** (#710, D-102), not `referral`: any host the host rules cover, except `ignore`d ones. A visit from the landing page to the app keeps the landing's channel.

- **The npm packages are `@openlens-obs/web` and `@openlens-obs/node`** (the `@openlens` scope was taken on npm). Both are published on release tags from v0.8.0 on, with the release's version; `npm.yml` failed before on every tag, since the package versions stayed at 0.1.0.

## [0.7.0] - 2026-11-27

### Added

- **Features touched by each release** (#576): each release read from GitHub has its changed files matched once, by the hourly pass, against the code paths of the feature map in force for it, and the result is kept (at most 100 features per release). The release verdict judges and lists the touched features first, with the same thresholds; the Releases page's notes, `releases.list`, `release_report` (MCP) and `releases.notes` show them with the files in no feature ("3 changed files match no feature"), or say that the map declares no code paths yet (`openlens-cli rules`). A feature's Releases tab and `feature_context` list the releases that changed it.
- **Code paths per feature** (#576, part 1): a feature map entry can list its code as globs from the repository root (`paths: ["src/export/**"]`; `*`, `**`, `?`, at most 20 per feature and 200 characters each, refused with the feature's name otherwise). The feature page shows them, `set_feature` (MCP) sets them, and `openlens-cli rules` asks the app's agents to keep them current. The matcher that turns a release's changed files into the features it touched is in place for the release verdict, which uses it in a later change.
- **Verdict written back to GitHub** (#575): once a production release is judged healthy or regressed, the hourly pass (right after the release notes are read) writes it where the app's agents look, with the repository and token tickets already use: a commit status `openlens/release` on the deployed commit (`success` or `failure`, linking to the Releases page when `OPENLENS_PUBLIC_URL` is set), a block in the GitHub release named like the release, one comment on each shipped pull request (at most 100 per release, edited when the verdict changes, never repeated), and on a regressed verdict an issue with the evidence and the replay links, filed as a ticket (a later verdict comments on it). Inconclusive verdicts and releases older than 7 days are not written. What was written is kept, so a restart or a second pass posts nothing twice; a refusal (the token lacks a permission) is shown on the Releases page and in `release_report` (`notes.write_back`) and given up after 5 tries per verdict. Text from outside (release names, pull request titles, error messages) is escaped so it cannot mention anyone, link or format.
- **Release notes from GitHub** (#574): for each release recorded with its commit range (`openlens-cli release`), an hourly pass reads from GitHub, with read-only calls and the repository and token tickets already use, the commits of the range, the merged pull requests they belong to, the files they changed and the tag or GitHub release named like it, and keeps them (at most 250 commits, 100 pull requests and 300 files per release, with "and K more"; no author is kept). The Releases page shows the notes grouped Added, Fixed, Changed; `releases.list`, `release_report` (MCP) and the new `releases.notes` command carry them, or say why they are not there (no GitHub link, no range, not read yet, reads failed). A GitHub error or rate limit is retried on the next pass, five times at most.
- **Runtime health per release from Node** (#610): the Node SDK's `express()` (or `captureRuntime()`) sends `$runtime_stats`: one at each process start, then one per 10-minute window with the event-loop delay p50 and p99 and the largest RSS and heap used, under OpenTelemetry's runtime metric names. `GET /api/projects/{id}/runtime` and the MCP tool `runtime` read it per release (restarts per day, RSS and its growth, loop delay p99); `release_report` carries the same as `runtime`. A release is *regressed* only when its restarts per day go up significantly (a crash loop); memory and loop delay are shown, never judged. Runtime stats never count as users or events.
- **Server errors and route stats from Node** (#593, #601): `captureException` sends a server exception as an error of kind *server*, grouped, alerted on and judged per release like a browser error; `express()` and `expressErrors()` (or `recordRequest` for other frameworks) count every request per route template and status code in 10-minute windows, as OpenTelemetry's `http.server.request.duration` histogram (semantic-convention attributes, seconds, default bounds), never one event per request; `captureUncaught()` is opt-in. The browser SDK adds an `x-openlens-session` header to same-origin requests (and to `traceOrigins`), so a server error carries its session and replay. OpenLens reads W3C trace context and never writes it: the app's own `traceparent` gives server errors and failed requests a `trace_id`, its sampling stays its own, and no `baggage` is added.
- **Error origin and the link to the session** (#624): each error group on the Errors page is tagged *Browser* or *Server*, with an *Origin* filter (`?origin=browser|server`, also on `GET /api/projects/{id}/errors`). A server group lists the browser sessions that made the request (the session the browser SDK sent, else the failed request with the same trace id), each linked to its replay when one was recorded. The `$server` pseudo user of server events counts in no user number: active users, retention, anonymous visitors, release shares, or an error group's users.
- **Server routes in the release verdict and the alerts** (#594): a route with 50 requests or more on both releases makes the release *regressed* when its 5xx share rises significantly (2 points at least) or its p95 is 1.5 times and 200 ms slower; new server errors are named as such. Every 10 minutes, a production route answering 5xx to 10 % or more of its last hour's requests (three times its usual share) opens an incident under *failing requests*. A feature map can declare its key actions (`server: ["POST /api/auth/sign-in"]`): their regressions are named, and their alert is urgent (quiet hours never hold it). The Errors page lists the server routes; `GET /api/projects/{id}/routes` and the MCP tool `routes` return them.
- **Job check-ins** (#609): a cron or background job checks in at the end of each run (`curl -X POST …/check-in/<key>/<slug>`, or `checkIn` in every server SDK), and OpenLens learns how often it runs (the median gap, after four check-ins, or `expectEvery`) and alerts once on the project's channels when a run is missed (no check-in for 1.5 times the usual gap), fails or takes twice its usual time; the next good check-in closes it. The Uptime page lists the jobs, with a switch (off by default) to count them in availability. `GET /api/projects/{id}/jobs` and the MCP tools `jobs`, `check_in` and `job_set`.
- **OpenTelemetry metrics over OTLP** (#605, D-085): `POST /v1/metrics` takes OTLP/HTTP metrics, in protobuf or JSON, with the project key (`x-openlens-key`, or `Authorization: Bearer <key>`), so a Collector or an app's own OpenTelemetry exporter sends to OpenLens with one header. It reads the `http.server.request.duration` histogram (explicit buckets, delta or cumulative; other bucket bounds are re-bucketed): each point counts in the routes, the release verdict and the alerts exactly like the Node SDK's route stats. Any other metric is answered as rejected in `partialSuccess`. A retry, an app restart or a server restart never counts a point twice. At most 4 MB and 10,000 points per request, under the same limits as `/capture` (a proxy in front needs a 4 MB body limit). Setup: "Already on OpenTelemetry" in `sdk/SERVER.md`.
- **Quality › Routes** (#622): a Routes tab (Errors · Routes · Replays) lists the server routes with their requests, share answered 5xx, p95 and p50, each with the previous release's value when it moved, a 10-day p95 trend and a *Key action* tag; key actions come first, then the routes that got worse. A summary line counts the requests, the 5xx share, the routes worse than the previous release and the degraded key actions. With no route stats, the page says how to send them. The Errors page keeps a one-card summary with a link.
- **The slowest request and the first 5xx of each route** (#607, #629, D-089): per route, status and stats window, the Node SDK keeps the slowest request and the first 5xx (its duration, time, trace id and browser session; never the user, a body, a header, a cookie or a query string), and the exemplars of OTLP points are read the same way, keeping only `session.id`. Quality › Routes shows a Slowest column and the first 5xx, each opening its replay at that moment when the session was recorded, else showing its trace id; the verdict's slower routes name their slowest request. `routes.list` (`GET /api/projects/{id}/routes`, MCP `routes`) returns them as `slowest` and `first_5xx`.
- **Outgoing dependencies** (#608, #630, D-090): the Node SDK's opt-in `captureOutgoing()` counts the app's outgoing HTTP calls (`fetch`, `http` and `https`) per method, external host, status and error class, as OpenTelemetry's `http.client.request.duration`; only the host is kept, never a path or a query, at most 50 hosts per window, and calls to OpenLens itself are left out. OTLP's `http.client.request.duration` is read too. A Dependencies table on the Errors page shows each host's calls, failed share and p95, with the release before when they moved. A host that got slower or fails more after a release is listed in the verdict's Backend group, shown and never judged. A production host that keeps failing for 15 minutes opens an incident under *failing requests*. `GET /api/projects/{id}/dependencies`, and the `dependencies` field of the MCP tool `routes`.
- **Backend in the release verdict** (#623): the verdict on the board and on the Releases page has a Backend group (routes worse on 5xx or p95, with their *Key* tag, new server error groups, "n other routes unchanged"), and a broken key action leads the headline. The Releases page lists the *Routes that got worse* with their requests, 5xx and p95 against before, top server error and up to 3 sessions each, linked to their replay when recorded (session ids only, never a user). With no server stats there is no Backend group and the verdict is unchanged.
- **A Runtime line per release** (#631): the Releases page shows each release's largest RSS and its growth, event-loop delay p99 and restarts per day next to the release before, with a compact line in the list, and says once how to call `ol.captureRuntime()` when there are no runtime stats. A crash loop leads the verdict's Backend group.
- **People › Retention** (#619): a new tab with the weekly cohort table (moved from the board) and a survival curve. Churn links to it instead of its own "How long they stay" list.

### Changed

- **The sidebar follows the method** (#621): Focus board, Ask, Releases, Live, Quality, Behaviour, People, Product, Settings, with access keys 1 to 9 in that order. Releases is its own section (Releases and Timeline, moved from Live); Goals moved from People to Product; Revenue is now a People tab. Every page keeps its URL.
- **The Focus board is rebuilt around the questions a product manager asks (UI v2.1)** (#614–#620, #623): top to bottom, a *Production right now* strip with App, Latest release, Incidents, Key actions and Setup, each one word, one line and a link, in place of the signals line (#614, #623); a lead card that, when the latest release is regressed, is its verdict: a plain headline from the worst check, the checks by layer, the next step, *Create ticket* and *Full verdict*, with the ranked insights cut to 4 rows and *Show all* (#615); five Outcomes tiles in place of Key numbers: Reach (active users in the window, today's as "N today, so far"), Value (tasks per session), Retention (churn rate), Quality (sessions with errors, and the share of server requests answered 5xx) and Speed (largest paint p75), plus Revenue when there is revenue, each opening its page with the board's filters (#616, #623); an *In flight* card beside the usage chart with goals and their progress, tickets with a GitHub issue followed from open to measured 14 days after their release, and flags switched on with their cohort result (#617); one Features table (adoption, users, completion, uses per user, role bars and signals such as *Stick driver* or *Churn exit*) in place of Feature pulse, Who uses what and Never used (#618); and one retention line comparing the oldest and newest complete cohorts (#619). Every other block moved to the page that owns it, one click away (#620): Web Vitals to Pages, the releases table to Releases, paths to value to Behaviour › Feature flow (*Paths to success*), funnels and journeys to each feature's Overview, flag cohorts to Flags, role gaps and the roles × features table to the Feature map, revenue to Revenue. Stickiness, average session and objectives at risk leave the board; objectives stay on Goals and in the digest.
- **Recordings kept a day follow the disk** (#606, #632, D-088): one disk budget (by default 80 % of the data volume minus what other files use, or `OPENLENS_DISK_BUDGET` as a share or a size) sets how many recordings each project keeps a day: 300 on a small host as before, up to 30,000 on a large one, and back toward 300, never below, as the disk fills. It is measured at most hourly. Retention does not move: 400 days of events and 30 days of recordings (D-015). The instance's Storage settings show a *What the disk allows* card with each value and why; `capacity.get`, `GET /api/capacity` (admin) and the MCP tool `capacity`. The replay rate text showed 300 whatever the budget; it now shows the number in force.
- **The route-stats window follows the disk** (#628, D-091): the server picks 10, 5 or 1 minute windows for route, dependency and runtime stats from the same budget and the number of routes (10 minutes stays the floor and the default), and tells the server SDKs in the `x-openlens-stats-window` header of `/capture`. The Node SDK follows it from its next flush; its one option `statsWindowSeconds` (60, 300 or 600) wins over the header. Routes, alerts, runtime and the verdict read any window, mixed windows in one day included. The window and its reason are in `capacity.get` and on the Storage card.
- **The stylesheet is cached for good** (#579): pages link `/assets/app/<hash>.css`, served as immutable for a year, so a browser fetches it once per release; `/assets/app.css` still answers for older pages. A test keeps it under its 23 kB compressed budget.

### Fixed

- **Self-hosting updates on Docker's containerd image store** (#597): `openlens-compose-update` could not go back to the previous image after a failed update, since an image whose tag the pull moved can no longer be named by its id; it now keeps the running image under the local tag `openlens-compose-update:previous` until the update is over. The Swarm stack (`deploy/swarm/openlens.yaml`) publishes port 8686 on its node (`mode: host`) instead of through the routing mesh, which never answered on some hosts and hid the client's address. The Swarm guide's daily cron line deploys the stack again (`docker stack deploy`) instead of `docker service update --image` with the same tag, which on Docker 29 leaves the service without a digest, after which no new image ever arrives.
- **A release's first visits stay in its window** (#568): the board's release window and its comparison were bounded by the query's own clock, read a moment after the window was set from the release's first event, so the first visits of a new release could be counted in the period before it. The bounds are now the instants the board resolved.
- **Lead time is measured** (#633): it was always *unknown*, since nothing recorded when a release's first commit was made. `openlens-cli release --commit` (and the `openlens-release` action) now reads the author time of the oldest commit of the release's range from the app's git history and records it (`first_commit_at` on `POST /api/projects/{id}/releases` and MCP `record_release`); Delivery's lead time runs from it to live. A shallow checkout or a first release leaves it unknown, and the CLI's `lead_time_note` says why: check out with `fetch-depth: 0`. With a GitHub link, the hourly read of each recorded range (#574) gives the first commit's time to releases recorded without it.
- **Change failure rate counts regressed releases** (#611): Delivery never saw the release verdicts, so it read *0 of 2 changes* while both releases were regressed. A change now fails when its release is judged regressed in the same environment (production unless another is asked for). The delivery API and the MCP call now compute the verdicts too.
- **No task time when the success event fires on entry** (#612): a feature whose success event fires as it starts (a `$pageview`, say) showed a task time of 0 s. Its Completion cell now shows "—" with a link to the Map health finding (a shared board keeps the dash, without the link).
- **The daily active users tile counted today's partial day** (#613): on a window, the headline was today's users so far. The Reach tile now counts the users active in the window, and today comes second as "N today, so far".
- **Logo colours**: the blob logo is back in its v1 colours (violet, blue, green, amber, pink); the v2 palette had turned it into the muted status tones.

## [0.6.0] - 2026-11-26

### Changed
- **The filter bar is a row of chips** (#542): the board's two filter forms and its help paragraph are replaced by the context chips in the top bar; the query parameters are unchanged (the team toggle is still `internal=1`). The page's date fields show the expected format, `YYYY-MM-DD` (#557).
- **Breakdown tabs keep every filter** (#548): they kept only the environment before. The Heatmap page offers a page picker and Clicks / Rage clicks / Scroll depth tabs when the data has them, and without a recording ranks the most clicked labels.
- **Storage settings never print the full data path** (#551): only its last part, so a home directory does not leak; the restore example uses placeholders.
- The default board is computed ahead only after the start-up work (identity backfill, first compaction and rollup pass), so the two no longer add up in memory.
- **The board page says how long it will wait** (#535, D-073): when its board is not cached and took a second or more to compute last time (or was never computed), the page shows a *Computing the board…* panel with *about N s* (the last compute time) or *a few seconds*, a small animation (none under reduced motion) and `role="status"`; it hides itself in CSS when the board arrives, with no script. A cached board, or one that took under a second last time, is sent whole with no panel.
- Task times resolve the feature map only for events within 30 minutes before a success; the default board page of each project is computed ahead in the background after startup and after new data while it is being looked at (#452, D-072). The numbers are unchanged.
- A board no longer holds its rollup rows in memory (#452, D-074): that copy, added in this release, saved little time and almost doubled the peak memory when several boards were computed together (430 to about 780 MB at 4 M events), and made boards fail under a 1 GiB limit; every board query reads the rollup files again. A board that fails because a query ran out of memory is computed once more, alone, after the other boards, instead of failing. The numbers are unchanged.
- Map health's `drift` reads the current release from the release states (#483 item 3, D-070): the environment's newest live release, or its newest rolling out when none is live, as the board's window does, instead of the release first seen last. A canary next to a live release, or a release rolled back, no longer reports its routes as new.
- CI: the four equivalence tests that roll up every closed day run with `cargo xtask ci --heavy` (nightly, release tags), not on every pull request, which went over 5 minutes.

### Added
- **A new dashboard look (UI v2)** (#558): one palette declared once for light and dark, a sidebar with a project monogram, a *Go to…* field and sections on `accesskey` 1–8, a user menu, a sticky top bar holding the breadcrumb and the period, environment, role, release and team chips (each opens a small form that keeps the other filters), the board's lead insight with a before/after comparison and the others as a ranked list, KPI tiles whose delta always says what it is compared with, data tables grouped by day with event pills, one explained empty state per page, form cards with numbered setup steps, segmented controls and switches, and new entry pages. Still no JavaScript, no inline style and no new setting (#539–#552). The design reference is `docs/design/ui-v2/`.
- **Go to…** (#541): a field in the sidebar takes a section, a feature (key, former key or name) or a person id and opens its page, or lists the matches; `GET /p/{id}/go?q=` (at most 200 bytes), engine command `goto.lookup`.
- **Confirmation without JavaScript** (#545): *Forget this person*, deleting a flag, *Delete the project* and *Sign out everywhere* sit in a danger card at the end of their page; their button opens the same page with `?confirm=<action>`, which shows the existing confirmation form in an open dialog. The handlers still require the same confirmation.
- **Motion** (#552): page-to-page view transitions, control feedback, content and charts drawing in, popover and dialog entrances, all in CSS and only when the system does not ask for less motion. A test fails when an animation sits outside `prefers-reduced-motion: no-preference` or animates a layout property.
- **Public status page** (#561, D-079): a project can publish a read-only page at `/status/<slug>`, without sign-in or cookie: the current state and since when, one line per component (production and the monitored environments the admin chose, under public names) with 90 daily bars, availability over 24 hours, 30 and 90 days, the response time when opted in and the SLO budget when a target is set, announcements, planned maintenance and the detected incidents of 90 days. Also `/status/<slug>.json`, an SVG badge (`/status/<slug>/badge.svg?window=state|24h|7d|30d|90d`) and an Atom feed (`/status/<slug>/feed.atom`). Off by default; the slug is unique across projects. No script, refreshes every minute, light and dark from the system. It never shows an address, a health path, an error text, an id, an event or a person. Requests are limited per address in a bucket of their own, a page is computed at most every 30 seconds, and an unknown or disabled page answers 404 with no body. Settings → Sharing, `GET`/`PUT /api/projects/{id}/status-page`, `openlens-cli status-page show|set|public`, MCP `status_page` and `status_page_set` (engine commands `status_page.get`, `status_page.set`, audited, and `status_page.public`).
- **Uptime history** (#559, D-075): the Uptime page shows the last 90 days as daily bars (green, amber under an hour down, red an hour or more, grey when not checked; hover a day for its availability and incidents), and every incident, page by page (the list used to stop at 100). One row per project, environment and UTC day is kept as long as the project; raw checks stay 7 days, except those from an hour before to an hour after an incident, kept a year. Monitored non-production environments keep their checks and days too, across restarts. `GET /api/projects/{id}/uptime/days?from=&to=&env=` (read, at most 400 days) and `GET /api/projects/{id}/incidents?before=&limit=`, `openlens-cli uptime` and `openlens-cli incidents`, and the MCP tools `uptime_days` and `incidents` (engine commands `uptime.days` and `uptime.incidents`).
- **Planned maintenance windows** (#563, D-076): declare a one-off window (start, end or length, components: `production` and/or environments, a text) from the Uptime page, the API (`/api/projects/{id}/maintenance`), `openlens-cli maintenance` or the MCP tools `maintenance` and `maintenance_set`, optionally announced once on the alert channels. While it runs the status reads *under maintenance* (`maintenance`), incidents of the covered components' down, traffic and failing-requests checks still open but send no alert and no reminder, and an outage still failing when it ends is announced then. Availability on the Uptime page and in `alerts.uptime` leaves the window's checks out and says how much time was left out. Windows can be extended or ended early while they run, and cancelled before they start; every change is audited.
- **Status announcements and incident updates** (#562, D-077): an announcement has a title, a plain-text body (at most 4,000 characters; markup is shown as text, `http(s)://` words become links), a level (information, degraded, outage, resolved), the components it concerns (production or environment names) and a start and optional end. It can follow a detected incident as dated updates (*investigating → identified → monitoring → resolved*): when the probe opens an incident, the Uptime page offers *Write an update*; when it closes it, the announcement stays open and the page proposes *Mark resolved*. At most one active information announcement is pinned (pinning one unpins the others). They are engine commands (`announcements.list`, `create`, `update`, `add_update`, `close`, `delete`, `send`; every write audited), on the Uptime page (admins write, everyone reads), the API (`/api/projects/{id}/announcements`, read scope to list, write scope to post), the CLI (`openlens-cli announce list|post|update|edit|close|delete|send`) and MCP (`announcements`, `announce`, `announcement_update`, `announcement_edit`, `announcement_close`, `announcement_delete`, `announcement_send`). Optionally sent to the alert channels too (one switch per project, off by default). Kept as long as the project (at most 1,000 per project, 100 updates each). The public status page that shows them is #561.
- **Availability over long windows and an availability target** (#560, D-078): the Uptime page, `GET /api/projects/{id}/status` (`availability`), `GET /api/projects/{id}/uptime/report`, `openlens-cli availability` and the MCP tool `availability` give each environment's availability over 24 hours, 7, 30, 90 and 365 days, this month and last month (time up over time measured: time with no check is shown as *not measured* and counts neither way; planned maintenance is left out and said), with incidents and p95. A project may set one target per environment over a rolling 30 days (`uptime.set_target`: the Uptime page, `PUT /api/projects/{id}/uptime/target`, `openlens-cli availability --target 0.999`, MCP `availability_target`); it then shows the error budget, what is spent and left, and the burn rate over the last hour and day, and two alert rules (on by default, switchable) announce *error budget spent* and *burning fast* (gone within 2 days at the last day's rate) once each.
- **SLSA Build level 3 provenance** (#473): each release carries `openlens-<tag>.intoto.jsonl`, and each published image a second provenance, made by the SLSA GitHub generator's isolated reusable workflows from the hashes alone, so the build cannot forge them. Check with `slsa-verifier verify-artifact` / `verify-image` ([Verify what you run](docs/deploy/README.md#verify-what-you-run)). The cosign signature and the GitHub attestations (level 2) stay.
- **Long boards run in the background** (#515, part 3 of #325, D-063): the *Run it* of a date range or past release that reads more than 30 days of events now starts a background job and opens its page, which refreshes itself (no JavaScript) with the time spent against the estimate, offers *Cancel*, and shows the board when it is done; the page can be left and reopened within the hour. A job is private to whoever started it (anyone else gets a 404), at most 2 compute at once per server (the others wait, queued), at most 8 are queued or running, and one per person. - **The board no longer keeps a 90-day copy of the events in memory** (#502, last part of #452, D-051): success events are read as a 30-day scan of the declared success events, Web Vitals as their 7-day scan of `$vital` rows, both from typed columns, and the insight cards, journeys, flag cohorts, funnels (now only their steps' events), task times, resurrected users and retention read their own window of days from the files. The board's memory no longer grows with the events of the window, and its 4 M-row cap (`BOARD_SNAPSHOT_ROWS`), the snapshot sharing of #418 and the limit of two boards computed at once are gone; a background rollup still waits for the boards being computed, and they for it. The metric `openlens_board_snapshots_total` is removed. Same numbers. The `scale` job re-measures time and memory.
- **The Coolify template follows the minor channel** (#198): `deploy/coolify/openlens.yaml` uses `:0.5` instead of `:latest`, so a redeploy brings fixes and never a behaviour change. Moving to the next minor is a choice, after its **Changed** section; `:latest` still follows every release.
- **Goals run as engine commands** (#494, D-042): setting, listing and deleting goals and objectives are now the `goals.*` commands of the engine, listed in a registry with the access level each needs; the Goals page, its forms, `GET`/`POST /api/projects/{id}/goals` and Ask's confirmed goal call them. Same checks, messages and answers as before.
- **Tickets run as engine commands** (#503, part of #308, D-042): drafting a ticket from a finding, filing or updating its GitHub issue, the tickets list with the learning log and the GitHub target are now the engine's `tickets.list`, `tickets.draft` (read), `tickets.file` and `tickets.target` (write) commands, and the hourly follow-up (closed issue, shipping release, before/after verdict) moved to the engine with them. The server keeps where the GitHub token comes from, sealing it, the HTTP calls and the schedule. Same pages, API answers, statuses, messages and audits as before.
- **Ask's tools run as engine commands** (#508, part of #308, D-057): the lookups of Ask OpenLens (`kpi`, `insights`, `feature_context`, `errors`, `sql`, `vitals`, `goals`, and the brief) are now the engine's `ask.board`, `ask.feature`, `ask.errors`, `ask.sql`, `ask.vitals` and `ask.goals` (read) commands, and proposing and applying a flag change use the new `flags.list` (read) and `flags.update` (write); the SQL tool's checks, its aggregate-only view and the per-project pseudonym key moved to the engine with them. The server keeps the tool loop, the model call (provider, key, HTTP), the text the model reads and the pending changes. Same prompts, tools, answers, refusals and confirmations as before.
- **Explore runs as engine commands** (#507, part of #308, D-042): a person's profile, the breakdown, acquisition, forms, churn, audience, flows, live and Web Vitals reports, the read-only SQL box and the win-back flag made from the users at risk are now the engine's `explore.person`, `explore.breakdown`, `explore.acquisition`, `explore.forms`, `explore.churn`, `explore.flag_audiences`, `explore.audience`, `explore.flows`, `explore.live` (read), `explore.sql`, `explore.make_audience` (write) and `explore.vitals` (admin, bearer only) commands, with the SQL that counts the active users of a win-back flag. The engine now reads flags and the recordings list itself (`openlens-flags`, `openlens-replay`). The pages, exports and `GET /api/projects/{id}/churn`, `/flows` and `/vitals` are adapters over them; the Revenue page and the exit-survey answers on Churn stay with the board and survey code. Same pages, API answers, statuses, messages and audits as before.
- **Alerts run as engine commands** (#499, part of #308, D-042): the alert settings, the app's status, the Uptime page's numbers and the test message are now the engine's `alerts.status`, `alerts.uptime`, `alerts.settings` (read), `alerts.set` and `alerts.test` (write) commands, and the logic of the minute pass (incidents, reminders, quiet hours, the *traffic stopped*, *failing requests*, certificate and regression checks, with their SQL) moved to the engine with them. The server keeps the probes, the certificate check, sending by email, webhook or ntfy, and the schedule. Same checks, messages, audits and timing as before.
- **Errors, acquisition and churn read typed columns** (#482, D-039): `$error` (`error_message`, `error_source`, `error_stack`), the landing facts of a `$pageview` (`acq_channel`, `acq_utm_source`, `acq_utm_campaign`, `acq_ref_host`), `$rating` of a `$vital` and `$rage` of a `$click` are now written as nullable columns next to `properties`, with `facts_version` on every new row, so the error groups, a feature's errors, the acquisition table and churn's friction no longer run a regular expression per row. Files written before are not rewritten: the `events` view reads their values from the text as before, and compaction fills the columns in. Same answers on old and new files.
- **Web Vitals read typed columns** (#449, D-037): each `$vital` is now stored with its facts as nullable columns next to `properties` (`vital_name`, `vital_value`, `vital_device`, `vital_el`, `vital_kind`, `vital_res` and the seven parts), so the board, the Web Vitals page and Goals no longer run a regular expression per row, and the board's 90-day snapshot no longer carries `properties` (the vitals have a 7-day snapshot of their own). Files written before have no such columns and are not rewritten: the `events` view reads their values from the text as before, and compaction fills the columns in. Same answers on old and new files.
- **The browser SDK sends `unknown`, not `production`, for a host no pattern matches** (#410, D-034): the project's host rules decide where it goes, and without one it is counted in no production number. The server reads `production` from older SDKs on such a host the same way, so they keep working, and an install whose upgrade seed has not run yet still stores these hosts as production.
- **Identity kept at ingestion** (#450, D-036): each `$identify` records which anonymous id belongs to which user, and gives every person a stable integer id, in the metadata store. Boards no longer re-read every `$identify` to merge visitors with their users; the numbers are the same. On upgrade, existing data is read once in the background, and until then nothing changes. Forgetting a person also removes these records.
- **A host nothing classifies is `unknown`, not production** (#410, D-034): it is kept out of production numbers until a rule says what it is. On upgrade, every host that sent production events in the last 30 days keeps a `production` rule. An environment set in the app (`init({ environment })`) still wins.
- **Password sign-in slows down instead of locking** (#428): after 3 failures in 15 minutes, each try for that email waits 1 s, 2 s, 4 s… up to 30 s, one at a time, so nobody can lock someone else out. One client address gets at most 30 failures per 15 minutes. Wrong current passwords on *My profile* count the same and are audited. The token holder can no longer create their account on an existing member's email.
- **Journal is the third M2 reference app** (#18): the docs and the roadmap describe it as wired outside this repo, with its `verify` result recorded by hand on #18 rather than replayed in CI.

### Fixed
- **"Paths to value" listed the same path twice** (#555) when two features share a success event; each path is now listed once and names every feature that shares it.
- **Raw ISO timestamps** (#556, #566) on the board's release table, in Settings → Environments and on the feature page's Replays tab now read like the other dates, in the project's time zone.

- **A board page loaded again is served from the cache at scale** (D-071): the second load of `/p/<project>` computed the whole board again (as slow as the first) on large projects. The cache was not the cause: the board failed intermittently at that size, and a failed board is not kept, so every page computed (and often failed) again. The likely failure is one of the board's dozen concurrent queries running out of the shared query memory only because the others ran beside it. Such a query now runs once more when the others are done (at most 10 s later), one such retry at a time; a query that runs out of memory alone still fails. A board that fails is now logged (`board not computed`), and the `scale` job warns when its cold board failed.
- **Capture no longer answers 503 "cannot store events" under load** (#510, D-065): since identity is kept at ingestion (#450), a batch with an `$identify` opened a metadata transaction that read before writing, and when the write lock was briefly taken by another connection SQLite failed it at once with "database is locked" instead of waiting (the nightly benchmark lost 1 to 4 requests a run). Metadata write transactions now take the lock when they begin and wait for it. A batch's `$identify` events (people, aliases and person ids) are also recorded in one metadata write instead of one per event plus one for the batch, and an import's people in one write; a batch without `$identify` still writes nothing.
- **Backups include the project icons** (#488): `openlens backup` (and scheduled backups) now copy `icons/`, so a restored server shows the icons at once instead of fetching them again. The session and secret key files stay out of backups on purpose; `docs/deploy/README.md` now says what a backup holds and what to do about the keys when restoring.
- **A cached board page is served from the cache as a whole** (#480): the revenue block of the board (and of the Revenue page) queried 30 days of event properties again on every load, so with a feature map that declares success events a board loaded twice took as long the second time as the first. The revenue is now computed with the board and cached with it, and follows new data the same way.

    - features that users who stay tried in their first 14 days (only users old enough to have had those 14 days count, so a longer life does not bias it);
    - friction on the last day (errors, rage clicks, failed requests, poor Web Vitals);
    - the place they left from;
    - the release they arrived on.
  - **Survival by role.**
  - **Win-back:** users who came back after churning, the release and feature they returned to, and how active they have been since.
  - **Explicit cancel:** the feature map may declare `churn_event` (D-019). A user who sends it counts as churned at once, and the answers of surveys triggered on it show as the exit survey.
  - **Users at risk:** admins can export them as CSV or JSON (audited, with CSV formulas neutralised). They can also turn the list into a flag that starts off, with a control group held out (`users` and `holdout` on flags). The churn page compares how active the nudged and held-out users were over the last 7 days.

- **Goals, part 2** (#272):
  - **Statuses for every KPI:** DAU, MAU, stickiness and feature success rates now have weekly series, so their status is no longer stuck at "not enough data". Web Vitals (LCP, INP, CLS at p75) can be goals too.
  - **Guardrails:** a goal can have up to two KPIs that must not get worse. The default limit is 5% worse than now, and it can be edited through the API. A breach is shown in red and raised as an alert (through the regression alerts toggle), and the alert closes once the KPI recovers.
  - **Objectives:** a sentence with 1–3 goals as key results and an end date. An objective takes the status of its weakest key result. When the period ends, it is archived as achieved or missed, with the final values. Open objectives that are at risk show at the top of the board.
  - **Deadlines in releases:** "in N releases", estimated from the median time between releases so far.
  - **What moved it:** the releases that changed the KPI most since the goal was set, with their effect, plus the flag, survey and map changes and notes in that period.

  - **API, MCP and CLI:** `POST /api/projects/{id}/goals` and the MCP tools `goals` and `set_goal`.

- **Flag targeting by property** (#279): a flag can carry up to 10 rules (`plan in pro, team`, `country not in FR`), all of which must match, on top of roles; accounts still bypass targeting. Rules test `plan`, `country` (from the address when not sent), `role`, `account` or any property passed to `identify(id, { properties })`; a user who did not send the property does not get the flag. The browser SDK and every server SDK (`plan`, `properties`) send them to `/flags`, which never stores them. Edit rules on the flag page, `openlens-cli flags set --rule '…'`, or MCP `flag_set { rules }`. The variants readout now compares each arm with the baseline (`control`, else the first variant): two-proportion p-values for the value and error rates, held to 0.05 shared between the arms (Bonferroni), and "too few" under 30.
- **Feature map quality** (#240): the map can declare `area` (one-level grouping), `requires` (features used first; unknown keys and loops are refused) and `renamed_from` (former keys, whose events count for the new one). ### Security

- **Ask's SQL tool returned person-level data when person-level detail was off** (SEC-01, GHSA-p52g-xmcm-2wrj): Ask queries an aggregate-only view (D-021).
- **The admin token was stored in plaintext** and reused as the session key (SEC-02, GHSA-v4mh-3vr2-7mxf): stored hashed, sessions have their own key.

### Fixed

- **Review before v0.3.0:**
  - **Admins and tokens limited to some projects stay in them.** Before this fix, a token could list other projects' keys and make install-wide calls, and an admin of one project could open install-wide pages (team, tokens, storage, AI) and widen their own reach.
  - **Forgotten people's recordings are dropped**, like their events. A rare race could also let a forgotten person's events back in until the next forget.
  - **The S3 listing works with a prefix set.** Before this fix, S3 backups were recorded as failed and the cold tier never moved a day.
  - **Backups:** the S3 backup is streamed from disk instead of read into memory, and a failed scheduled backup is tried again at the next tick instead of waiting a full period.
  - **Email sign-in:** made-up addresses no longer use up the hourly sending budget.
  - **Country and cookieless visitors** follow the same proxy rule as the rate limits (D-022).
  - **A person's export** refuses to be partial (more than 200,000 events), and checks the disk before reading cold days back.
  - **Smaller fixes:**
    - share embed origins must be exactly `localhost` or `127.0.0.1` over plain http;
    - the public-address check sees IPv4 inside IPv6 (NAT64, 6to4);
    - the TLS check reads `https://[v6]`;
    - the first-start owner link has the Coolify host;
    - long non-ASCII paths no longer crash a backup.

- **Board queries no longer slow ingestion down** (#295): DataFusion runs on its own threads, apart from the ones serving HTTP; `/capture` gunzips and parses batches off the async threads; the forgotten people of a project are kept in memory instead of one lookup per event.
- **Project pages need a session** (#294): the flag and survey edit pages were readable without signing in. Every `/p/…` page now refuses anonymous visitors in one place (login redirect, or 401 for JSON and CSV), and a test walks every route of the router as an anonymous visitor, a viewer of another project and a viewer.
- **Ingestion limits follow the connection** (D-022): `/capture`, `/r` and `/flags` count clients by their connection address and trust `X-Forwarded-For` only from a private proxy; the check runs before the body is read. Writes get 503 when less than 5 % of the data volume is free.
- **One cross-site check for every dashboard form** (#294): a middleware refuses any state-changing request that the browser marks as cross-site (`Sec-Fetch-Site`), or whose `Origin` is another site, instead of a check repeated in each handler. Ingestion and the bearer API are not affected; clients that send neither header (curl, the CLI) are let through.
- **Captures no longer wait for a flush** (#293): only the hand-over of the buffered events runs under the writer lock; the Parquet segments are written outside it, and a failed write is retried by the next flush. `xtask bench` reports p99.9 and the maximum latency, over 60 s by default.
- **Flushes and compactions survive a power cut** (#292): the directory of each new segment, and the WAL directory, are synced before the WAL or the old segments are removed.
- **Ask's SQL without person-level detail runs on an aggregate-only view** (D-021): no ids, URLs, properties or people tables; people are counted with `count(DISTINCT user_key)`; groups of fewer than 5 people are left out.
- **The board is computed once and shared** (#291): pages that show it reuse one result per project and filters until new data lands, concurrent requests wait for the same computation, and at most 2 boards are computed at once. A second visit answers from memory instead of recomputing for seconds.
- **Page URLs are stored without their query string** (#290), as `docs/privacy.md` promised: the query and the fragment are dropped at capture, except the campaign tags `utm_*`, `ref` and `gclid`. URLs already stored are cleaned once at startup.
- The churn page failed with a feature map pushed ("last place" query). It now works with and without a map.
- **Going back a release right after an upgrade works again**: two starts in the same second named their upgrade copy the same, and the second refused to start. Copies now take the next free second. (The upgrade check waits between steps for releases up to v0.2.0.)

## [0.2.0] - 2026-11-22

### Added

- **Fresh base images:** Renovate pins the Dockerfile base images by digest and updates them. Every month CI rebuilds the newest stable image from the same code on a fresh base image, so OS security fixes reach installs on `latest` or a minor channel (#201).
- **Release train:** every Tuesday, CI releases the version in development when the changelog has entries, the nightlies are green and nothing is labelled `release-blocker` or `release-hold`. It then publishes the binaries, image and chart, and moves `main` to the next minor version. No human step (#197).
- **Safe upgrades:** on start, OpenLens backs up the data when the version changed, in `backups/upgrade/` (only the latest copy is kept), before it migrates anything. It refuses to start on data written by a newer release, which stops a rollback to an older image from damaging it. The data directory records both in `openlens-version.json` (#199).
- **A time zone per project** (D-017): days and weeks of every KPI (DAU series, active days, retention weeks, resurrected users, tasks per user-day) start in the team's zone. Set it with `openlens-cli init --timezone Europe/Paris`, `openlens-cli timezone <project> <zone>`, `PATCH /api/projects/{id}` or the MCP `set_timezone` tool. It is `UTC` until set, and the projects page shows it (#152).
- **Server SDKs for Go, Ruby and PHP** (`sdk/go`, `sdk/ruby`, `sdk/php`), standard library only, with the same calls as Node and Python: capture, feature, identify and flags. CI tests each one (#157).
- **Replay player:** the session's events as markers on the timeline (page views, successes, forms, clicks, rage clicks, errors), with a legend, a list of events that follows the playhead (click one to jump), ±10 s, speed 0.5× to 8×, keyboard shortcuts (Space, J/L, ←/→, +/−), and a phone layout (#170).
- **Releases ship Linux aarch64 binaries** next to x86_64 (built on GitHub's ARM runners, free for public repositories).
- **Upgrade check in CI:** before an image is published, `scripts/upgrade-check.sh` starts the last release on a fresh volume, writes events, a flag and a feature map, then starts the new image on that volume and requires the same events, people, sessions, projects, keys, flags and feature map, and a board that loads (#158).
- **Delete a project:** `DELETE /api/projects/{id}?confirm={id}` or `openlens-cli delete-project <id> --confirm <id>` removes its events, replays, source maps, people, flags, surveys and feature map. The id must be given twice.
- **Rate limits on `/capture`** for traffic coming through a proxy: 50 requests/s per client address (burst 500) and 20,000 events/s per project key (burst 200,000), with `429` and `Retry-After`, which the SDK honours. Direct connections (server SDKs in the cluster, benchmarks) are not limited (#160).
- **Sign-in by email:** with SMTP and the public URL set, the login page offers "Email me a login link" to invited users. Links work once, within 15 minutes. The answer is the same whether the address exists, the link is built from the configured URL (never the request's Host), and requests are rate-limited (#155).
- **Robots at capture:** events posted by crawlers, link previews and uptime monitors (by user agent) are stored in the `bot` environment, out of every production number. `verify` reports `robots_last_day` (#154).
- **Internal users:** `identify(id, { internal: true })` marks the team's own accounts. The board leaves them out unless *Include the team* is ticked (`internal=1` in the API) (#153).
- **Kubernetes:**
  - a Helm chart (`deploy/helm/openlens`): one replica, PVC, a generated admin token kept across upgrades, an optional Ingress with TLS, a hardened pod, and optional features from Secrets;
  - a Kustomize base rendered from the chart;
  - the agent guide [docs/deploy/kubernetes.md](docs/deploy/kubernetes.md);
  - a CI job installing and upgrading both on kind;
  - the chart published to `oci://ghcr.io/philippe-arnd/charts` on release tags.
- **Backups:** `openlens backup --into <dir> --keep N` names each copy after the UTC time and keeps the newest N. The chart's `backup.enabled` runs it nightly as a CronJob next to the server, onto the data volume or `backup.existingClaim`.
- **CLI:** plain HTTP is accepted for cluster-internal servers (`http://<service>:8686`, `*.svc`, `*.cluster.local`, private addresses), so an agent inside the cluster can use it.

### Fixed

- **Security pass before v0.2:**
  - the capture rate limit reads the client address from the last `X-Forwarded-For` entry, the one the proxy added, so a client can no longer pick its own;
  - the theme and sidebar links refuse to return to a path a browser could read as another site (`/\host`);
  - CI checks dependencies against RustSec advisories (`cargo deny check advisories`).
  - SQLite 3.54.1, which fixes CVE-2026-119375 (RUSTSEC-2026-0459): crafted database and `-wal` files could make queries return stale memory. It is a local vector. rusqlite goes from 0.37 to 0.43.
- **Board on large projects:** the in-memory snapshot keeps only the columns the board reads, and `properties` only for Web Vitals. That is about 160 bytes per event, so the in-memory cap rises from 2 M to 4 M events in 90 days. At 2.2 M events, the board went from 6–7 s to 3.7 s on one vCPU (#190).
- **Faster board with identities:** the identified-users filter is decided once per board (from the `persons` count) instead of as an `OR` of subqueries that DataFusion could not plan as a semi-join, and the all-time totals skip the identity join. The board on 368 k events with anonymous visits went from 1.7 s to 0.8 s on one vCPU. `xtask bench` now sends realistic anonymous visits, and `RUST_LOG=openlens_query=debug` logs what each query costs (#159).
- **New events could stay out of the dashboards until a restart (v0.1.0).** DataFusion caches directory listings with no expiry, and the runtime shared by every query kept the first list of files it saw: events that arrived later, and compacted days, were not read. The listing cache is now off; Parquet footers are still cached. A regression test writes segments between queries of one engine.
- **Phones:** every dashboard page fits a 390 px screen. Grids never get wider than the screen, wide tables scroll inside their card, the navigation scrolls sideways, filters and tiles stack, and touch targets are 44 px. The nightly browser check now opens every page on a phone and fails if one scrolls sideways (#170).
- **Accessibility:** the light theme's muted text, links, badges and statuses now meet WCAG AA contrast (4.5:1), and links inside text are underlined. The nightly browser check runs axe-core on every page, light and dark, and fails on any serious or critical issue (#161).
- Form submits inside web components (open shadow roots) are captured, with their `data-feature` (#151).
- A resent batch is stored once: the server drops event uuids it stored recently (the last 100k), and compaction keeps one row per uuid per day (#150).
- The replay recorder and player bundles now carry rrweb's MIT notice, which minification had stripped (`sdk/js/licenses/rrweb-LICENSE.txt`).

### Changed

- **Image tags are update channels:** `:latest` is now the newest *stable* release, where until now it followed `main`. `:0.2` follows the patches of a minor version, and `:edge` follows `main`. A stable release can redeploy a Coolify instance by itself (secrets `COOLIFY_DEPLOY_URL` and `COOLIFY_TOKEN`), and the dashboard footer shows the version and *Update available* (one daily GET to GitHub, `OPENLENS_UPDATE_CHECK=off` to disable) (#198).
- **Build releases on every merge:** each code change on `main` is published as `vX.Y.Z-YYMMDD-sha` (version in development, UTC date, commit), with the binaries, SDK bundles, chart, checksums, image and notes. They are marked pre-release until `vX.Y.Z` is tagged.
- **Navigation is a sidebar on the left**, collapsible to icons only. Collapse and Expand links remember the choice in a cookie (no script), and phones always get the icon rail. It holds the project switcher, the project's pages (with Digest), the current page marked, the theme and Log out (#170).
- **No more automatic `default` project.** Agents create one project per app (`openlens-cli init --name <app>`). A `default` project is created only when `OPENLENS_PROJECT_KEY` is set (CI, demos, templates that want a key at once). With no project, the home page points to `/agents.md`. The admin token is logged once, when it is generated.
- **README** redesigned: wordmark, section links, architecture diagram, how it works, dated performance numbers, known limits and releases.
- **Releases** are built by CI (`publish.yml`): every `v*` tag gets Linux binaries, the SDK bundles, the Helm chart and `SHA256SUMS`, with notes from `docs/releases/` or the CHANGELOG and a *Full changelog* link. Pre-release snapshots of `main` can be made by hand; they are not published to npm.
- Docs: the clean-room source log lists every public source used so far; `target-app-parity.md` and `gaps.md` match v0.1.0.

## [0.1.0] - 2026-11-22

The first release. OpenLens is a self-hosted product analytics tool in one Rust binary. Agents wire it into an app, and the product manager opens a board that already says where the value is.

### Added

#### Ingestion and storage

- `POST /capture`: batched and gzip-aware ingestion with a key per project, size and depth limits, clock-skew correction and safe handling of hostile input.
- A write-ahead log, then daily Parquet partitions (zstd), with compaction and crash recovery.
- SQLite metadata: projects, keys, persons, role history, flags, surveys and users.
- Every event carries its environment and release (D-012).
- Fixed retention: events are kept for 400 days, replays for 30 days.
- `openlens backup <dir>` makes a consistent copy while the server runs.
- An optional S3 copy of closed days and a daily metadata snapshot, signed with our own SigV4.

#### Browser SDK `@openlens/web` (4.6 kB gzipped)

- One script tag (`/c.js`) or the npm package.
- **Autocapture:**
  - page views, including History API and `#/` routes, back/forward cache and prerendering;
  - clicks named by `data-feature`, also inside web components;
  - form submits and rage clicks;
  - scroll depth, errors, Web Vitals and failed requests.
- **Identity:** `identify(id, { role, account, plan })`, which links the anonymous visit before login; `reset()`; sessions shared across tabs.
- **Delivery:** failed sends are retried with the same event ids. Crawlers and monitoring robots are not captured.
- **Privacy:**
  - no cookies;
  - input values are never captured;
  - Do Not Track and consent modes are respected;
  - `data-openlens-mask`, `-block` and `-ignore` give finer control.
- **Session replay** (rrweb, MIT) loads lazily from `/r.js`, with every input masked.
- **Feature flags:** `isEnabled`, plus `$flags` on every event.
- **Micro-surveys:** `/s.js`, one question after a success event.

#### Server SDKs

- Node and Python thin HTTP clients with no dependencies ([sdk/SERVER.md](sdk/SERVER.md)).

#### The method and the Focus board

- **Feature map** (`openlens.features.yaml`): features, entry points, success events, steps and canonical roles. The CLI lints it against the code.
- **KPIs by role, account, plan, page, feature, environment and release** ([docs/kpis.md](docs/kpis.md)):
  - DAU/WAU/MAU, stickiness and resurrected users;
  - sessions, bounce rate and tasks;
  - error rate and Core Web Vitals.
- **Insight cards**, each with its evidence, cohort size and next step:
  - stick drivers and the value moment;
  - churn points, friction and role blind spots;
  - release regressions, slow pages and funnel drops;
  - flag wins and regressions, with significance tests.
  - A card shows only once a group has 8 or more users.
- **Board sections:**
  - feature pulse (adoption, frequency, active days, completion, task time p50/p90);
  - roles × features;
  - weekly retention cohorts;
  - journeys into each success event, and funnels from the declared steps;
  - release vs release, environment vs environment.
- **Errors:** grouped by fingerprint and split by role, release and page, with source maps per release and links to replays.
- **Pages:** scroll depth, the most-clicked elements, rage clicks, and a visual click heatmap over a recorded visit of the real page.
- **Weekly digest:** a page, the MCP `digest` tool, and an optional Monday email over SMTP.
- **LLM rewording of cards:** optional. Numbers are guarded and the originals are kept.

#### Agents

- **`openlens-cli`:** `init`, `features lint|push`, `import` (backfill), `verify`, `sourcemaps`, `flags`, `surveys`, `export`, `sql`, `login-link`, `rules` and `guide`.
- **MCP server** (`openlens-cli mcp`) with every command, plus `insights`, `kpi_report`, `user_timeline`, `errors`, `board` and `digest`.
- **Agent guides** ([wire.md](docs/agents/wire.md), also served at `/agents.md`, and [analyze.md](docs/agents/analyze.md)):
  - framework recipes for Next.js, Nuxt, SvelteKit, Astro, Remix, Vite SPAs, Angular and server-rendered apps;
  - a strict Content Security Policy;
  - an ad-blocker proxy through the app's domain.
- **Reference apps** in `examples/` (a script-tag app and an SPA), clicked through nightly in a real browser until `verify` is green.

#### Dashboard and access

- Server-rendered pages with no JavaScript and a strict CSP. Only the replay player runs a script, under its own CSP.
- Light and dark themes, and a project switcher.
- **Sign-in:** the admin token, one-time login links, and optional single sign-on with OpenID Connect (code flow with PKCE; invited emails only).
- **Accounts:** admin and viewer users, optional access per project, and invites by login link. The first login creates your admin account.

#### Operations

- A Docker image on GHCR (`ghcr.io/philippe-arnd/openlens`) and a one-click Coolify template, with no required environment variables.
- A healthcheck and a benchmark (about 80k events/s on one vCPU).
- **CI:**
  - a fast PR gate (fmt, clippy, tests, layers, licences);
  - the browser e2e and dashboard screens under the real CSP;
  - the image smoke test;
  - an issue opened automatically when `main` breaks.

### Changed

These changes concern instances that ran pre-release builds:

- **SQL:** `events` is now a view over the stored `raw_events`, where anonymous ids that `identify` linked are replaced by the user. `persons` and `person_aliases` are new tables.
- **User counts:** DAU/WAU/MAU, retention and cohorts count identified users only. Visitors who never logged in show as "not logged in". A project that never calls `identify` still counts everyone.
- **Script tag:** the server defaults to the directory `c.js` came from, path included, instead of its origin. That is the same for `https://lens.example.com/c.js`, and makes a proxied `/_l/c.js` work.
- **SDK `reset()`** does nothing while nobody is identified.

### Fixed

- A visit that starts before login no longer counts as two users.
- A single-page session counts as a bounce: `$scroll`, `$vital` and `$identify` no longer count as activity.
- A task counts once, as its success event, instead of once per event of the feature.
- Retention and stick-driver cohorts use the first `identify` ever, so returning users are no longer taken for new ones.
- Clicks on masked elements send no text or link.

### Security

- Every input is treated as hostile: bounded sizes, a rejection list per event, no `unwrap`/`panic` in production code, and read-only SQL scoped to one project with time, memory and row caps.
- HMAC session cookies (`HttpOnly`, `SameSite=Lax`), and origin checks on dashboard forms.
