# Decisions

Append-only. Each entry: id, date, decision, why, consequences.

## D-001 (2026-11-21) Rust + DataFusion + Parquet, single binary
**Why:** lean self-hosting (one process, one volume) with columnar analytics performance. **Consequences:** funnels, retention and paths are written as DataFusion aggregate functions, and there is no external database.

## D-002 (2026-11-21) Licence AGPL-3.0-only; dependencies limited to a permissive allowlist
**Why:** self-hosters are free; anyone hosting a modified version must publish it. Dependencies stay permissive so that combining them is never in doubt. **Consequences:** `deny.toml` enforces the allowlist, and MPL-2.0 is allowed only per crate and unmodified.

## D-003 (2026-11-21) Rust everywhere except the browser SDK (UI part superseded by D-011)
**Why:** the SDK runs inside the customer's own pages. It must be tiny, needs no WebAssembly, and session recording relies on the rrweb recorder (MIT). **Consequences:** `sdk/js` is TypeScript, kept under 10 kB gzipped without replay. All other code, including the UI, is Rust (see D-011).

## D-004 (2026-11-21) Roles and features are first-class concepts
**Why:** the main users are PMs who ask "which roles use which features". **Consequences:** `identify()` takes `role`/`account`/`plan`. These are promoted to columns and copied onto events at capture time. The feature catalog lives in `meta`, and the default dashboard is the roles × features matrix (M3).

## D-005 (2026-11-21) Agent wiring returns plans, not free-form edits (superseded by D-013)
**Why:** "add one dependency and let an agent wire it" only scales if every edit can be reviewed and verified. **Consequences:** `crates/wire` outputs a typed install plan, applied by `openlens-cli wire` or returned through MCP. `openlens-cli verify` closes the loop.

## D-006 (2026-11-21) The feature map is an explicit file that agents maintain in the app repo
**Why:** most target apps are vibecoded or maintained by agents. Features inferred from clicks are noisy, while a declared map (entry points, success event, steps) is precise, can be reviewed in PRs, and is cheap for agents to keep current. **Consequences:** `openlens.features.yaml` has a JSON Schema, `features push` / `features lint`, a rules snippet injected into the app's AGENTS.md, and versioned feature keys on the server.

## D-007 (2026-11-21) Simple UI, deep agent access
**Why:** PMs want patterns ("what makes users stick", "where they churn", "which journeys create value"), not a query builder. Agents can do the deep analysis if given clean data. **Consequences:** the UI is limited to three questions plus drill-down. Every analysis is also an MCP tool returning a compact summary with drill-down ids. Raw data is exported as Parquet/JSONL with a stable documented schema, and read-only SQL is exposed to agents.

## D-008 (2026-11-21) Home screen is the Focus board, an insights feed rather than a builder
**Why:** a PM opening OpenLens wants to know where the value is and what to focus on, not to build charts. **Consequences:** M3 ships ranked, evidence-backed insight cards generated by engine commands (the same ones agents call through MCP). The empty state is honest about missing data and wiring gaps. Any LLM wording pass is optional and cannot alter the numbers.

## D-009 (2026-11-21) Roles are declared and matched in the feature map, and history-aware
**Why:** role is the key dimension for every KPI. Free-text roles sent by apps drift (`owner`, `Admin`, `superadmin`). **Consequences:** canonical roles plus match rules live in `roles:`; raw values are kept; unmatched values raise role-gap cards; role changes are stored with their date, and events carry the role the user had at event time.

## D-010 (2026-11-21) KPI catalog with fixed definitions; errors and Web Vitals move to M1
**Why:** Phil's key KPIs cover users (DAU/MAU, churn, session duration, tasks), performance (errors, CWV) and features (most/least used, longest tasks), all split by role. **Consequences:** `docs/kpis.md` is the contract for the UI, MCP and exports. A "task" is formally a feature entry → success event. Basic error capture and CWV ship in the M1 SDK, while M7 keeps deep grouping and source maps.

## D-011 (2026-11-21) UI is server-rendered HTML (maud), not Leptos/WASM
**Why:** it is leaner still: there is no wasm toolchain, no client bundle, the binary is smaller, it works without JS, and it is trivially accessible. The dashboard is read-mostly (KPI strips, ranked cards, tables), which server rendering handles well. Charts are SVG generated in Rust. **Consequences:** `crates/ui` renders HTML with `maud` (MIT/Apache). Interactivity uses links and forms, and live tail uses periodic refresh. The only JS shown in the dashboard will be the vendored rrweb player on the replay page (M6), plus OpenLens's own SDK for dogfooding. This supersedes the Leptos part of D-003.

## D-012 (2026-11-21) Environment and release are first-class dimensions
**Why:** PMs compare releases to know whether a change moved a KPI, and they keep staging and preview traffic away from production numbers. **Consequences:** every event carries `environment` and `release` columns. The SDK detects them automatically (`localhost`/`127.*`/preview hosts → `development`, hosts starting with `staging.` → `staging`, otherwise `production`; release from `init({release})`, `<meta name="openlens-release">` or the script tag's `data-release`). The dashboard defaults to production and compares the current release with the previous one. Environments are a column, not separate projects, so one key serves all of them.

## D-013 (2026-11-21) Coherence pass: the method first, less machinery
**Why:** the vision grew message by message, and some parts contradicted others or were over-built. **Changes:**
- `docs/method.md` (map → measure → focus → act → compare, day zero with no human setup) is the reference. ROADMAP is reorganised around it: 7 milestones instead of 10.
- The MCP server arrives in M2, not M9, because agent tools depend on it. Login (admin token plus a one-time link) arrives in M1, not M9, because the dashboard exists from M1.
- **The codemod engine is dropped** (supersedes D-005): agents already edit code well. OpenLens provides `init`, `features lint`, `verify`, `import` and a guide, and the agent makes the edits. `crates/wire` becomes `crates/featuremap`.
- **History is backfilled** from the app's own data (`openlens-cli import`), so the first login has insights.
- The M2 exit uses 3 reference apps, not 8. Fun names are cut back to the method's own concepts.
- Deferred to "Later": weekly digest, LLM rewording, micro-surveys, experiment significance, server SDKs.

## D-014 (2026-11-21) Almost no configuration: a methodology, not a toolbox
**Why:** OpenLens is a method carried out by a tool. Every knob is a decision pushed onto the user, and a way for two projects to stop being comparable. **Consequences:**
- The server needs **no** environment variables. The few it reads (`OPENLENS_DATA_DIR`, `OPENLENS_ADMIN_TOKEN`, `OPENLENS_PROJECT_KEY`, `OPENLENS_ADDR`) are optional overrides for deploy templates.
  - *Amended 2026-11-24 (#318):* optional features added since (D-016: SMTP, LLM, OIDC, S3, GitHub, GeoIP, alerts, the update check) read their own variables, and are all off until set. The full list is in `docs/deploy/README.md`. `cargo xtask env-docs` (part of `cargo xtask ci`) fails when the server reads a variable that page does not document.
- The **feature map is the only project configuration**, and agents write it. Its one tunable is `churn_after_days`.
- Sessions (30-minute gap), the task timeout (30 minutes), UTC days and KPI definitions are fixed (docs/kpis.md).
- There is no dashboard builder or chart configurator. A request for a new knob needs a decision entry explaining why a fixed default cannot work.

## D-015 (2026-11-22, accepted by Phil) Fixed retention, one volume, no OIDC yet
**Why:** M6 listed OIDC, TTL, an S3 backend and backups. We apply D-014 and keep only what a self-hosted deploy needs to run for months without supervision. **Consequences:**
- **Retention is fixed.** Events are kept for 400 days (a little over 13 months), so a month can be compared with the same month a year earlier. Replays are kept for 30 days after their last chunk. The background job deletes older data every 10 minutes. Backfilled history older than 400 days is dropped too. There is no setting for either.
- **Storage is one local volume.** It is the data dir, mounted as a volume. Backups are a consistent copy of that directory, made by `openlens backup` (SQLite online backup plus a copy of the immutable Parquet and replay files). The S3 backend moves to Later.
- **OIDC moves to Later.** The persona gets in through one-time login links sent by an agent, and the admin token covers the rest. OIDC would add three settings, JWT crypto and an outbound dependency on the IdP, for a team-SSO need that has not come up yet.

## D-016 (2026-11-22, Phil) The Later list is built, as defaults or optional add-ons
**Why:** Phil asked for every Later item: experiment significance, visual heatmaps, weekly digest, server SDKs, in-app micro-surveys, LLM rewording of cards, multi-user permissions, OIDC and an S3 backend. This partly supersedes D-015. D-014 still holds: a fresh deploy needs no setting. **Consequences:**
- **Always on, nothing to set:** significance on flag cohorts, heatmap overlays, the digest page, server SDKs, micro-surveys (defined by agents through the API, like flags), and users with roles (admin and viewer, invited by login link).
- **Optional, and off until configured** (environment variables documented in `docs/deploy/README.md`):
  - SMTP for the emailed digest;
  - an LLM endpoint and key for rewording cards (the original wording is always kept);
  - OIDC (issuer, client id and secret);
  - S3 (bucket and credentials) as a second copy of closed partitions.

  Each one is skipped silently when it is not configured.
- Local disk remains the source of truth. S3 receives closed days and backups, so losing the bucket never loses data.

## D-017 (2026-11-22, Phil) A time zone per project

**Decision:** each project has one IANA time zone (`Europe/Paris`), `UTC` until set. Days and weeks of every KPI start in it: the DAU series, active days, user-days, tasks per user-day, resurrected users, retention weeks (Monday), and the day a session belongs to.

**Why:** in Paris, a UTC "today" starts at 01:00 (02:00 in summer), so the evening's activity lands on the wrong day. Guessing the zone from the browsers was the alternative, but it changes silently when the audience moves, and it is wrong for a team that serves another continent.

**Consequences:**
- It is one setting, so it goes against D-014. The agent sets it once, at `openlens-cli init --name <app> --timezone <zone>`, from where the team works. `openlens-cli timezone <project> <zone>`, `PATCH /api/projects/{id}` or the MCP `set_timezone` tool change it later. It is not an environment variable, and it is not in the feature map.
- Rolling windows ("last 24 h", "last 7 days") do not depend on it.
- Storage stays in UTC. Partitions are UTC days, so changing the zone rewrites nothing.
- The SDK still starts a new session when the UTC day changes, because the browser does not know the project's zone. A session belongs to the local day it starts in.

## D-018 (2026-11-22, Phil) Times follow the reader, the project's zone is the default

**Decision:** every time shown and every day or week bucket follows the time zone of the person reading (#215). It supersedes D-017 for display. The project's zone stays as the default: for readers who chose none, for the admin API and the CLI without `--tz`, and for scheduled digests.

**Why:** a team spread over several zones reads the same board. The events stay in UTC, so the reader's zone is only a view.

**Consequences:**
- The order is: the reader's zone (*My profile*, `/me`; the owner's is a setting), then `?tz=` on the API (`openlens-cli --tz` / `OPENLENS_TZ`), then the project's zone, then UTC.
- Nothing is detected in the browser: the dashboard runs no script (strict CSP), and without a choice a reader sees what D-017 showed, so nothing changes by itself.
- Caches stay valid: the board snapshot holds UTC rows, and buckets are computed per query.

## D-019 (2026-11-23, agent for #269) An explicit cancel event, optional, in the feature map

**Decision:** the feature map may declare `churn_event` (for example `subscription_cancelled`). A user who sends it counts as churned at once, without waiting for `churn_after_days`. Without it nothing changes.

**Why:** an app that knows when someone cancels should not wait two weeks to count them, and a survey triggered on that event is the natural exit survey. It follows D-014: there is no new setting, only one more optional fact about the app, declared where the other facts already live.

**Consequences:**
- Churn rate, survival and at-risk lists treat a cancel as the end of a life, on the day it was sent.
- The churn page shows the cancels and the answers of the surveys triggered on that event.
- Older servers refuse a map with the field, because the format is strict. Upgrade the server before pushing the map.

## D-020 (2026-11-23, agent for #244) Ask runs server-side, without a script, and only proposes changes

**Decision:** the AI chat is its own page, `/p/{id}/ask`. The page is server-rendered with a form: the answer arrives whole after the tool loop, with no streaming script. The model reads through server-side tools that return aggregates. It writes nothing itself: a change is a proposal that an admin applies with a single-use, server-issued token. Providers are `anthropic` or `openai-compatible`, configured by `OPENLENS_LLM_*` or Settings → AI, with the key sealed by the secret store from #218.

**Why:**
- The dashboard stays script-free under its strict CSP (D-013).
- A prompt injection planted in event names cannot cause a write.
- One OpenAI-compatible mode covers LiteLLM, OpenRouter, Azure, Mistral, vLLM and a local Ollama with no extra code.

**Consequences:**
- There is no live streaming. A long investigation (up to 4 tool rounds) takes as long as the model needs.
- The tools live in the server (`ask.rs`) and call the same engine functions as the REST API. MCP keeps going through the REST API.
- Person-level SQL is refused unless an admin allows it per project.
- Each project has a daily token budget (`OPENLENS_LLM_DAILY_TOKENS`, 400,000 by default), and each person may ask 30 questions an hour.


## D-021 (2026-11-23, agent for the audit) Ask's SQL without person-level detail runs on an aggregate-only view

**Decision:** when a project does not allow person-level detail, the `sql` tool of Ask runs in its own query context. There, `events` is a view with only `event, timestamp, path, feature, role, plan, release, environment, flags, date`, plus `user_key` and `session_key`: an HMAC-SHA256 of the user and session ids, keyed by a secret kept per project (`project:<id>:ask_key`, never shown). `persons`, `person_aliases` and `raw_events` do not exist there. The plan must end in an aggregate, without window functions or subqueries above it, and every group of fewer than **5** distinct people is dropped. The threshold is fixed (D-014).

**Why:** the first filter searched words in the SQL text, and three plain queries got around it (a window function, the `persons` table, `person_aliases`). Checking what the query can reach, and what its plan returns, does not depend on how it is written.

**Consequences:**
- Small projects (fewer than 5 people in a group) get empty results from Ask's SQL; the other Ask tools still answer.
- A query that renames `user_key` below the aggregate is refused rather than guessed.
- With person-level detail allowed, `events` is the full table (with the feature map applied), and `user_key` and `session_key` are the ids themselves.

## D-022 (2026-11-24, agent for the audit) Ingestion limits follow the connection, and stop on a full disk

**Decision:** `/capture`, `/r` and `/flags` count each client by the address of its connection. `X-Forwarded-For` (last entry) or `X-Real-IP` is believed only when the connection comes from the host or a private network (loopback, RFC 1918, link-local, IPv6 unique local): the reverse proxy of Coolify, Compose or a cluster. Direct local traffic with no such header (a server SDK on the host, `xtask bench`) is not limited. The per-client check runs before the body is decompressed or parsed. Writes are refused with 503 and `Retry-After` when less than **5 %** of the data volume is free. Both rules are fixed (D-014).

**Why:** the project key is public, and a limit that only applied to proxied traffic left a directly exposed server (`docker run -p`, a systemd binary) with none, while a client could pick a new address for every request by forging the header.

**Consequences:** a proxy on a public address in front of OpenLens makes every client look like the proxy; put it on a private network, as every supported deployment does.

## D-023 (2026-11-24, agent for #321) The board's snapshot cap stays at 4 M rows; larger apps wait for daily rollups

**Decision:** `BOARD_SNAPSHOT_ROWS` stays at 4 M rows and the default window stays at 90 days. The supported size for one small server is **up to about 4 M events in 90 days** (about 45,000 a day), where the board comes from memory. Above it the board still works, but reads the files: at 63 M events it took 22 s on first load and 12 s after that, with 2.6 GB of server memory, on 4 vCPU. The way past it is the daily rollups of #223 (#325, #326), not a bigger snapshot.

**Why:** a snapshot of 63 M rows would need about 10 GB at 160 bytes a row, far above the 1 GB target (D-001). Rollups make the board's cost depend on the number of days, not the number of events.

**Consequences:** the sizing docs give the 4 M limit and the memory needed above it. Above that size, people should expect a slow board until the rollups ship. The `scale` job of `perf.yml` measures the same thing again after each change.

## D-024 (2026-11-24, agent for #317) What a beta release promises

**Decision:** until the end of M6, OpenLens is beta (0.x). A minor release may change behaviour, and a change that asks for action is marked **Breaking:**. Stored events stay readable by newer servers with no migration (columns are only added). Feature-map fields are only added and are optional, and the server is upgraded before a map that uses a new one. The SDKs keep working against newer servers. Once `/api/v1` exists (#312), a field or endpoint is removed only after one minor release of deprecation. The policy lives in docs/stability.md.

**Why:** someone choosing OpenLens needs to know what an upgrade can break. The promises are the ones the code already keeps: a fixed table schema that reads older files, a strict map parser, additive SDK fields.

**Consequences:** a change to the event schema adds a column and never renames one. A change that would break one of these promises waits for a major version, or is announced as **Breaking:** with the steps to follow.

## D-025 (2026-11-24, agent for #322) Rollups by 15-minute UTC bucket, gone with the events

**Decision:** closed days are rolled up into `person_q` (person, bucket, environment, release, role: events, errors, first and last time) and `metric_q` (bucket, environment, release, role, event, feature: events, distinct people). Buckets are 15 minutes wide in UTC, so a reader in any zone rebuilds their own days exactly (D-018 stays true). A day is closed a full day after it ends. People are the merged person, as in every query. The rollups are deleted when someone is erased and rebuilt from the events left, and they are pruned with their day, so they never outlive the events. Rebuilt after an alias merge? No: a day rolled up stays as written until an erasure or a schema change, a small drift accepted for now. The schema version is in the path (`rollups/v1/`), so a new one rolls everything up again.

**Why:** a day bucket in UTC cannot give a Paris or Kolkata day, and fifteen minutes covers every real offset. Keeping rollups past the events would change the retention promise of docs/privacy.md, which is for the owner to decide (#323, #325). Vitals and feature sets wait for the board to read rollups (#323), where their shape is known.

**Consequences:** the tables are about as many rows as person-sessions, far fewer than events. No setting is added; older installs roll up their history on their own, seven days per project every ten minutes.

## D-026 (2026-11-24, owner for #322) Rollups outlive the events

**Decision:** event days are still deleted after 400 days, but their rollups (`person_q`, `metric_q`) stay as long as the project does, so the board and investigations can look further back (#323, #325). Erasing someone removes them from every rollup: a day that still has its events is rolled up again without them, and an older day loses their `person_q` rows; its `metric_q` keeps only counts. Deleting a project deletes its rollups. Rollups are backed up with the rest. This replaces the "gone with the events" part of D-025.

**Why:** the owner wants to look back further than the raw retention. Rollups hold no URL, property or session id: per person only counts, the role, release and environment.

**Consequences:** rollups cannot be rebuilt once their events are gone, so their schema only gains nullable columns; a new rollup version converts the old tree instead of dropping it. docs/privacy.md says what is kept, and for how long.

## D-027 (2026-11-24, agent for #310) SQL values are bound, or quoted in one place

**Decision:** a value reaches SQL through `openlens-sqlgen` only. Filter values from a request (environment, role, release) are bound as named placeholders (`$env`, `$role`, `$release`) that DataFusion fills in (`QueryEngine::with_params`): they are never part of the query text. Where a placeholder cannot go (inside a view, such as the feature map's projection, or a cast's type), `sqlgen::quote` makes the literal, after `sqlgen::checked` (1-200 bytes, no control character) or the map's validation, which applies the same rule. `cargo xtask sql-guard`, part of `ci`, fails when quotes are doubled anywhere else.

**Why:** two hand-written escapes with different rules, spread over a dozen files, were one forgotten call away from an injection. One crate with no dependency can be used from the feature map and the engine alike.

**Consequences:** a new filter value is bound with `Params::set` or `bind`, never formatted in. Every value taken from a request is bound (part 2: events, people, pages, replays, data exports). Values from the feature map or a stored definition (success events, steps, variants) stay quoted literals, checked at upload.

## D-028 (2026-11-24, agent for #324) Page rollups, and clicks lose their detail after 30 days

**Decision:** each closed day also gets `click_q` (clicks per page and click-map cell, with rage clicks and viewport widths), `label_q` (the 20 most clicked labels per page) and `scroll_q` (sessions per page by deepest scroll, in 10 % steps), split by environment, release and role. These are UTC days, because a heatmap needs no local day. After 30 days, once the day has its rollups, `$click` events lose `$text`, `$tag`, `$id`, `$href`, `$x`, `$y` and `$vw`. The event row, its page, `$feature` and `$rage` stay, because churn reads rage clicks over 90 days. The 30 days are fixed (D-014).

**Why:** click labels are the most personal text the SDK sends, and positions are most of a click's bytes. Nothing reads them past 30 days, and the rollups keep what a longer view would need.

**Consequences:** a day is trimmed only after its rollups are written, so the history of an older install is rolled up before it is trimmed. Adding three tables to `rollups/v1` makes every stored day roll up again once, seven per pass.
