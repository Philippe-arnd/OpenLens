# Decisions

Append-only. Each entry: id, date, decision, why, consequences.

## D-001 (2026-11-21) Rust + DataFusion + Parquet, single binary
**Why:** lean self-hosting (one process, one volume) with columnar analytics performance. **Consequences:** funnels, retention and paths are written as DataFusion aggregate functions, and there is no external database.

## D-002 (2026-11-21) Licence AGPL-3.0-only; dependencies limited to a permissive allowlist
**Why:** self-hosters are free; anyone hosting a modified version must publish it. Dependencies stay permissive so that combining them is never in doubt. **Consequences:** `deny.toml` enforces the allowlist, and MPL-2.0 is allowed only per crate and unmodified.

## D-003 (2026-11-21) Rust everywhere except the browser SDK (UI part superseded by D-011)
**Why:** the SDK runs inside the customer's own pages. It must be tiny, needs no WebAssembly, and session recording relies on the rrweb recorder (MIT). **Consequences:** `sdk/js` is TypeScript, kept under 10 kB gzipped without replay. All other code, including the UI, is Rust (see D-011).

## D-004 (2026-11-21) Roles and features are first-class concepts
**Why:** the main users are PMs who ask "which roles use which features". **Consequences:** `identify()` takes `role`/`account`/`plan`. These are promoted to columns and copied onto events at capture time. The feature catalog lives in `meta`, and the default dashboard is the roles × features matrix (M3).

## D-005 (2026-11-21) Agent wiring returns plans, not free-form edits (superseded by D-013)
**Why:** "add one dependency and let an agent wire it" only scales if every edit can be reviewed and verified. **Consequences:** `crates/wire` outputs a typed install plan, applied by `openlens-cli wire` or returned through MCP. `openlens-cli verify` closes the loop.

## D-006 (2026-11-21) The feature map is an explicit file that agents maintain in the app repo
**Why:** most target apps are vibecoded or maintained by agents. Features inferred from clicks are noisy, while a declared map (entry points, success event, steps) is precise, can be reviewed in PRs, and is cheap for agents to keep current. **Consequences:** `openlens.features.yaml` has a JSON Schema, `features push` / `features lint`, a rules snippet injected into the app's AGENTS.md, and versioned feature keys on the server.

## D-007 (2026-11-21) Simple UI, deep agent access
**Why:** PMs want patterns ("what makes users stick", "where they churn", "which journeys create value"), not a query builder. Agents can do the deep analysis if given clean data. **Consequences:** the UI is limited to three questions plus drill-down. Every analysis is also an MCP tool returning a compact summary with drill-down ids. Raw data is exported as Parquet/JSONL with a stable documented schema, and read-only SQL is exposed to agents.

## D-008 (2026-11-21) Home screen is the Focus board, an insights feed rather than a builder
**Why:** a PM opening OpenLens wants to know where the value is and what to focus on, not to build charts. **Consequences:** M3 ships ranked, evidence-backed insight cards generated by engine commands (the same ones agents call through MCP). The empty state is honest about missing data and wiring gaps. Any LLM wording pass is optional and cannot alter the numbers.

## D-009 (2026-11-21) Roles are declared and matched in the feature map, and history-aware
**Why:** role is the key dimension for every KPI. Free-text roles sent by apps drift (`owner`, `Admin`, `superadmin`). **Consequences:** canonical roles plus match rules live in `roles:`; raw values are kept; unmatched values raise role-gap cards; role changes are stored with their date, and events carry the role the user had at event time.

## D-010 (2026-11-21) KPI catalog with fixed definitions; errors and Web Vitals move to M1
**Why:** Phil's key KPIs cover users (DAU/MAU, churn, session duration, tasks), performance (errors, CWV) and features (most/least used, longest tasks), all split by role. **Consequences:** `docs/kpis.md` is the contract for the UI, MCP and exports. A "task" is formally a feature entry → success event. Basic error capture and CWV ship in the M1 SDK, while M7 keeps deep grouping and source maps.

## D-011 (2026-11-21) UI is server-rendered HTML (maud), not Leptos/WASM
**Why:** it is leaner still: there is no wasm toolchain, no client bundle, the binary is smaller, it works without JS, and it is trivially accessible. The dashboard is read-mostly (KPI strips, ranked cards, tables), which server rendering handles well. Charts are SVG generated in Rust. **Consequences:** `crates/ui` renders HTML with `maud` (MIT/Apache). Interactivity uses links and forms, and live tail uses periodic refresh. The only JS shown in the dashboard will be the vendored rrweb player on the replay page (M6), plus OpenLens's own SDK for dogfooding. This supersedes the Leptos part of D-003.

## D-012 (2026-11-21) Environment and release are first-class dimensions
**Why:** PMs compare releases to know whether a change moved a KPI, and they keep staging and preview traffic away from production numbers. **Consequences:** every event carries `environment` and `release` columns. The SDK detects them automatically (`localhost`/`127.*`/preview hosts → `development`, hosts starting with `staging.` → `staging`, otherwise `production`; release from `init({release})`, `<meta name="openlens-release">` or the script tag's `data-release`). The dashboard defaults to production and compares the current release with the previous one. Environments are a column, not separate projects, so one key serves all of them.

## D-013 (2026-11-21) Coherence pass: the method first, less machinery
**Why:** the vision grew message by message, and some parts contradicted others or were over-built. **Changes:**
- `docs/method.md` (map → measure → focus → act → compare, day zero with no human setup) is the reference. ROADMAP is reorganised around it: 7 milestones instead of 10.
- The MCP server arrives in M2, not M9, because agent tools depend on it. Login (admin token plus a one-time link) arrives in M1, not M9, because the dashboard exists from M1.
- **The codemod engine is dropped** (supersedes D-005): agents already edit code well. OpenLens provides `init`, `features lint`, `verify`, `import` and a guide, and the agent makes the edits. `crates/wire` becomes `crates/featuremap`.
- **History is backfilled** from the app's own data (`openlens-cli import`), so the first login has insights.
- The M2 exit uses 3 reference apps, not 8. Fun names are cut back to the method's own concepts.
- Deferred to "Later": weekly digest, LLM rewording, micro-surveys, experiment significance, server SDKs.

## D-014 (2026-11-21) Almost no configuration: a methodology, not a toolbox
**Why:** OpenLens is a method carried out by a tool. Every knob is a decision pushed onto the user, and a way for two projects to stop being comparable. **Consequences:**
- The server needs **no** environment variables. The few it reads (`OPENLENS_DATA_DIR`, `OPENLENS_ADMIN_TOKEN`, `OPENLENS_PROJECT_KEY`, `OPENLENS_ADDR`) are optional overrides for deploy templates.
  - *Amended 2026-11-24 (#318):* optional features added since (D-016: SMTP, LLM, OIDC, S3, GitHub, GeoIP, alerts, the update check) read their own variables, and are all off until set. The full list is in `docs/deploy/README.md`. `cargo xtask env-docs` (part of `cargo xtask ci`) fails when the server reads a variable that page does not document.
- The **feature map is the only project configuration**, and agents write it. Its one tunable is `churn_after_days`.
- Sessions (30-minute gap), the task timeout (30 minutes), UTC days and KPI definitions are fixed (docs/kpis.md).
- There is no dashboard builder or chart configurator. A request for a new knob needs a decision entry explaining why a fixed default cannot work.

## D-015 (2026-11-22, accepted by Phil) Fixed retention, one volume, no OIDC yet
**Why:** M6 listed OIDC, TTL, an S3 backend and backups. We apply D-014 and keep only what a self-hosted deploy needs to run for months without supervision. **Consequences:**
- **Retention is fixed.** Events are kept for 400 days (a little over 13 months), so a month can be compared with the same month a year earlier. Replays are kept for 30 days after their last chunk. The background job deletes older data every 10 minutes. Backfilled history older than 400 days is dropped too. There is no setting for either.
- **Storage is one local volume.** It is the data dir, mounted as a volume. Backups are a consistent copy of that directory, made by `openlens backup` (SQLite online backup plus a copy of the immutable Parquet and replay files). The S3 backend moves to Later.
- **OIDC moves to Later.** The persona gets in through one-time login links sent by an agent, and the admin token covers the rest. OIDC would add three settings, JWT crypto and an outbound dependency on the IdP, for a team-SSO need that has not come up yet.

## D-016 (2026-11-22, Phil) The Later list is built, as defaults or optional add-ons
**Why:** Phil asked for every Later item: experiment significance, visual heatmaps, weekly digest, server SDKs, in-app micro-surveys, LLM rewording of cards, multi-user permissions, OIDC and an S3 backend. This partly supersedes D-015. D-014 still holds: a fresh deploy needs no setting. **Consequences:**
- **Always on, nothing to set:** significance on flag cohorts, heatmap overlays, the digest page, server SDKs, micro-surveys (defined by agents through the API, like flags), and users with roles (admin and viewer, invited by login link).
- **Optional, and off until configured** (environment variables documented in `docs/deploy/README.md`):
  - SMTP for the emailed digest;
  - an LLM endpoint and key for rewording cards (the original wording is always kept);
  - OIDC (issuer, client id and secret);
  - S3 (bucket and credentials) as a second copy of closed partitions.

  Each one is skipped silently when it is not configured.
- Local disk remains the source of truth. S3 receives closed days and backups, so losing the bucket never loses data. *Amended by D-031 and D-032: with the cold tier turned on, days older than 120 days live on S3 only.*

## D-017 (2026-11-22, Phil) A time zone per project

**Decision:** each project has one IANA time zone (`Europe/Paris`), `UTC` until set. Days and weeks of every KPI start in it: the DAU series, active days, user-days, tasks per user-day, resurrected users, retention weeks (Monday), and the day a session belongs to.

**Why:** in Paris, a UTC "today" starts at 01:00 (02:00 in summer), so the evening's activity lands on the wrong day. Guessing the zone from the browsers was the alternative, but it changes silently when the audience moves, and it is wrong for a team that serves another continent.

**Consequences:**
- It is one setting, so it goes against D-014. The agent sets it once, at `openlens-cli init --name <app> --timezone <zone>`, from where the team works. `openlens-cli timezone <project> <zone>`, `PATCH /api/projects/{id}` or the MCP `set_timezone` tool change it later. It is not an environment variable, and it is not in the feature map.
- Rolling windows ("last 24 h", "last 7 days") do not depend on it.
- Storage stays in UTC. Partitions are UTC days, so changing the zone rewrites nothing.
- The SDK still starts a new session when the UTC day changes, because the browser does not know the project's zone. A session belongs to the local day it starts in.

## D-018 (2026-11-22, Phil) Times follow the reader, the project's zone is the default

**Decision:** every time shown and every day or week bucket follows the time zone of the person reading (#215). It supersedes D-017 for display. The project's zone stays as the default: for readers who chose none, for the admin API and the CLI without `--tz`, and for scheduled digests.

**Why:** a team spread over several zones reads the same board. The events stay in UTC, so the reader's zone is only a view.

**Consequences:**
- The order is: the reader's zone (*My profile*, `/me`; the owner's is a setting), then `?tz=` on the API (`openlens-cli --tz` / `OPENLENS_TZ`), then the project's zone, then UTC.
- Nothing is detected in the browser: the dashboard runs no script (strict CSP), and without a choice a reader sees what D-017 showed, so nothing changes by itself.
- Caches stay valid: the board snapshot holds UTC rows, and buckets are computed per query.

## D-019 (2026-11-23, agent for #269) An explicit cancel event, optional, in the feature map

**Decision:** the feature map may declare `churn_event` (for example `subscription_cancelled`). A user who sends it counts as churned at once, without waiting for `churn_after_days`. Without it nothing changes.

**Why:** an app that knows when someone cancels should not wait two weeks to count them, and a survey triggered on that event is the natural exit survey. It follows D-014: there is no new setting, only one more optional fact about the app, declared where the other facts already live.

**Consequences:**
- Churn rate, survival and at-risk lists treat a cancel as the end of a life, on the day it was sent.
- The churn page shows the cancels and the answers of the surveys triggered on that event.
- Older servers refuse a map with the field, because the format is strict. Upgrade the server before pushing the map.

## D-020 (2026-11-23, agent for #244) Ask runs server-side, without a script, and only proposes changes

**Decision:** the AI chat is its own page, `/p/{id}/ask`. The page is server-rendered with a form: the answer arrives whole after the tool loop, with no streaming script. The model reads through server-side tools that return aggregates. It writes nothing itself: a change is a proposal that an admin applies with a single-use, server-issued token. Providers are `anthropic` or `openai-compatible`, configured by `OPENLENS_LLM_*` or Settings → AI, with the key sealed by the secret store from #218.

**Why:**
- The dashboard stays script-free under its strict CSP (D-013).
- A prompt injection planted in event names cannot cause a write.
- One OpenAI-compatible mode covers LiteLLM, OpenRouter, Azure, Mistral, vLLM and a local Ollama with no extra code.

**Consequences:**
- There is no live streaming. A long investigation (up to 4 tool rounds) takes as long as the model needs.
- The tools live in the server (`ask.rs`) and call the same engine functions as the REST API. MCP keeps going through the REST API.
- Person-level SQL is refused unless an admin allows it per project.
- Each project has a daily token budget (`OPENLENS_LLM_DAILY_TOKENS`, 400,000 by default), and each person may ask 30 questions an hour.


## D-021 (2026-11-23, agent for the audit) Ask's SQL without person-level detail runs on an aggregate-only view

**Decision:** when a project does not allow person-level detail, the `sql` tool of Ask runs in its own query context. There, `events` is a view with only `event, timestamp, path, feature, role, plan, release, environment, flags, date`, plus `user_key` and `session_key`: an HMAC-SHA256 of the user and session ids, keyed by a secret kept per project (`project:<id>:ask_key`, never shown). `persons`, `person_aliases` and `raw_events` do not exist there. The plan must end in an aggregate, without window functions or subqueries above it, and every group of fewer than **5** distinct people is dropped. The threshold is fixed (D-014).

**Why:** the first filter searched words in the SQL text, and three plain queries got around it (a window function, the `persons` table, `person_aliases`). Checking what the query can reach, and what its plan returns, does not depend on how it is written.

**Consequences:**
- Small projects (fewer than 5 people in a group) get empty results from Ask's SQL; the other Ask tools still answer.
- A query that renames `user_key` below the aggregate is refused rather than guessed.
- With person-level detail allowed, `events` is the full table (with the feature map applied), and `user_key` and `session_key` are the ids themselves.

## D-022 (2026-11-24, agent for the audit) Ingestion limits follow the connection, and stop on a full disk

**Decision:** `/capture`, `/r` and `/flags` count each client by the address of its connection. `X-Forwarded-For` (last entry) or `X-Real-IP` is believed only when the connection comes from the host or a private network (loopback, RFC 1918, link-local, IPv6 unique local): the reverse proxy of Coolify, Compose or a cluster. Direct local traffic with no such header (a server SDK on the host, `xtask bench`) is not limited. The per-client check runs before the body is decompressed or parsed. Writes are refused with 503 and `Retry-After` when less than **5 %** of the data volume is free. Both rules are fixed (D-014).

**Why:** the project key is public, and a limit that only applied to proxied traffic left a directly exposed server (`docker run -p`, a systemd binary) with none, while a client could pick a new address for every request by forging the header.

**Consequences:** a proxy on a public address in front of OpenLens makes every client look like the proxy; put it on a private network, as every supported deployment does. Without a proxy, publish the port so the server sees real client addresses (`docker run -p` with Docker's userland proxy makes every client come from the bridge gateway, a private address, whose `X-Forwarded-For` is then believed): put a reverse proxy in front, as the deploy guides do. The same rule now gives the country and the cookieless visitor (review of v0.3.0).

## D-023 (2026-11-24, agent for #321) The board's snapshot cap stays at 4 M rows; larger apps wait for daily rollups

**Decision:** `BOARD_SNAPSHOT_ROWS` stays at 4 M rows and the default window stays at 90 days. The supported size for one small server is **up to about 4 M events in 90 days** (about 45,000 a day), where the board comes from memory. Above it the board still works, but reads the files: at 63 M events it took 22 s on first load and 12 s after that, with 2.6 GB of server memory, on 4 vCPU. The way past it is the daily rollups of #223 (#325, #326), not a bigger snapshot.

**Why:** a snapshot of 63 M rows would need about 10 GB at 160 bytes a row, far above the 1 GB target (D-001). Rollups make the board's cost depend on the number of days, not the number of events.

**Consequences:** the sizing docs give the 4 M limit and the memory needed above it. Above that size, people should expect a slow board until the rollups ship. The `scale` job of `perf.yml` measures the same thing again after each change.

*Note (2026-11-27):* the snapshot and its 4 M cap are gone since D-051 (#502); the board reads rollups and bounded scans instead.

## D-024 (2026-11-24, agent for #317) What a beta release promises

**Decision:** until the end of M6, OpenLens is beta (0.x). A minor release may change behaviour, and a change that asks for action is marked **Breaking:**. Stored events stay readable by newer servers with no migration (columns are only added). Feature-map fields are only added and are optional, and the server is upgraded before a map that uses a new one. The SDKs keep working against newer servers. Once `/api/v1` exists (#312), a field or endpoint is removed only after one minor release of deprecation. The policy lives in docs/stability.md.

**Why:** someone choosing OpenLens needs to know what an upgrade can break. The promises are the ones the code already keeps: a fixed table schema that reads older files, a strict map parser, additive SDK fields.

**Consequences:** a change to the event schema adds a column and never renames one. A change that would break one of these promises waits for a major version, or is announced as **Breaking:** with the steps to follow.

## D-025 (2026-11-24, agent for #322) Rollups by 15-minute UTC bucket, gone with the events

**Decision:** closed days are rolled up into `person_q` (person, bucket, environment, release, role: events, errors, first and last time) and `metric_q` (bucket, environment, release, role, event, feature: events, distinct people). Buckets are 15 minutes wide in UTC, so a reader in any zone rebuilds their own days exactly (D-018 stays true). A day is closed a full day after it ends. People are the merged person, as in every query. The rollups are deleted when someone is erased and rebuilt from the events left, and they are pruned with their day, so they never outlive the events. Rebuilt after an alias merge? No: a day rolled up stays as written until an erasure or a schema change, a small drift accepted for now. The schema version is in the path (`rollups/v1/`), so a new one rolls everything up again.

**Why:** a day bucket in UTC cannot give a Paris or Kolkata day, and fifteen minutes covers every real offset. Keeping rollups past the events would change the retention promise of docs/privacy.md, which is for the owner to decide (#323, #325). Vitals and feature sets wait for the board to read rollups (#323), where their shape is known.

**Consequences:** the tables are about as many rows as person-sessions, far fewer than events. No setting is added; older installs roll up their history on their own, seven days per project every ten minutes.

## D-026 (2026-11-24, owner for #322) Rollups outlive the events

**Decision:** event days are still deleted after 400 days, but their rollups (`person_q`, `metric_q`) stay as long as the project does, so the board and investigations can look further back (#323, #325). Erasing someone removes them from every rollup: a day that still has its events is rolled up again without them, and an older day loses their `person_q` rows; its `metric_q` keeps only counts. Deleting a project deletes its rollups. Rollups are backed up with the rest. This replaces the "gone with the events" part of D-025.

**Why:** the owner wants to look back further than the raw retention. Rollups hold no URL, property or session id: per person only counts, the role, release and environment.

**Consequences:** rollups cannot be rebuilt once their events are gone, so their schema only gains nullable columns; a new rollup version converts the old tree instead of dropping it. docs/privacy.md says what is kept, and for how long.

## D-027 (2026-11-24, agent for #310) SQL values are bound, or quoted in one place

**Decision:** a value reaches SQL through `openlens-sqlgen` only. Filter values from a request (environment, role, release) are bound as named placeholders (`$env`, `$role`, `$release`) that DataFusion fills in (`QueryEngine::with_params`): they are never part of the query text. Where a placeholder cannot go (inside a view, such as the feature map's projection, or a cast's type), `sqlgen::quote` makes the literal, after `sqlgen::checked` (1-200 bytes, no control character) or the map's validation, which applies the same rule. `cargo xtask sql-guard`, part of `ci`, fails when quotes are doubled anywhere else.

**Why:** two hand-written escapes with different rules, spread over a dozen files, were one forgotten call away from an injection. One crate with no dependency can be used from the feature map and the engine alike.

**Consequences:** a new filter value is bound with `Params::set` or `bind`, never formatted in. Every value taken from a request is bound (part 2: events, people, pages, replays, data exports). Values from the feature map or a stored definition (success events, steps, variants) stay quoted literals, checked at upload.

## D-028 (2026-11-24, agent for #324) Page rollups, and clicks lose their detail after 30 days

**Decision:** each closed day also gets `click_q` (clicks per page and click-map cell, with rage clicks and viewport widths), `label_q` (the 20 most clicked labels per page) and `scroll_q` (sessions per page by deepest scroll, in 10 % steps), split by environment, release and role. These are UTC days, because a heatmap needs no local day. After 30 days, once the day has its rollups, `$click` events lose `$text`, `$tag`, `$id`, `$href`, `$x`, `$y` and `$vw`. The event row, its page, `$feature` and `$rage` stay, because churn reads rage clicks over 90 days. The 30 days are fixed (D-014).

**Why:** click labels are the most personal text the SDK sends, and positions are most of a click's bytes. Nothing reads them past 30 days, and the rollups keep what a longer view would need.

**Consequences:** a day is trimmed only after its rollups are written, so the history of an older install is rolled up before it is trimmed. Adding three tables to `rollups/v1` makes every stored day roll up again once, seven per pass.

## D-029 (2026-11-24, agent for #326) One long query at a time; compacted days sorted for pruning

**Decision:** free-form queries (Ask, the SQL page, `POST /api/.../sql`) are cold: at most one runs at a time, and a second one fails at once with "another long query is running" (503 with `Retry-After` on the API) instead of queueing. The board and the pages are hot and never wait for the gate. A query that runs out of the memory pool says so plainly instead of returning DataFusion's error. When a closed day is compacted, its rows are sorted by event then time and written in 64k-row groups with page statistics, so a query on one event or a short range reads only the groups that hold it. Days already compacted keep their layout until their next rewrite.

**Why:** one person's large Ask question must not slow the board for everyone, or the ingestion that shares the runtime. Sorting costs nothing at read time and lets DataFusion's row-group pruning work.

**Consequences:** no setting (D-014). The S3 cold tier is part B of #326.

## D-030 (2026-11-24, agent for #312) The API contract: `/api/v1`, a typed route table, closed error codes

**Decision:** `/api/v1/...` is the versioned API, and `/api/...` is the same routes under an alias that stays. The contract is a hand-written table in `crates/server/src/openapi.rs` (method, path, token scope, summary), served as OpenAPI 3.1 at `/api/openapi.json`. A test fails when the table and the routes in the source differ. Errors are `{"code", "message"}` with a code from a closed list (`crates/server/src/apierr.rs`), plus `error` for one release. The ingestion endpoints keep answering SDKs with status codes only.

**Why:** a table checked against the source costs less than annotating every handler with a new dependency, and it cannot drift. Clients act on codes, so messages can improve without breaking them.

**Consequences:** a new API route needs a line in the table, and CI says so. Removing a route or a field from `/api/v1` follows D-024: one minor release of deprecation first.

## D-031 (2026-11-24, agent for #326, owner's go) With S3 set, old event days live on S3 only

**Decision:** when S3 is configured, an event day older than **120 days** moves to S3. It moves only once its rollups exist, its upload is current, and S3 lists every one of its files at the same size. A marker `cold/project=<p>/date=<d>` records it. 120 rather than 90 days, because goals read 112 days of raw events: every dashboard view keeps working. Forgetting someone also reaches cold days: each one is brought back, rewritten without them, sent up again (new objects first, old ones deleted), and moved off the disk again, by the hourly S3 job. A person's export brings the project's cold days back first. Cold days older than 400 days are deleted from S3 (D-015). Without S3 nothing changes. This amends D-016 for those days: S3 is then their only copy.

**Why:** a long-lived install keeps its disk to the last four months of raw events, while rollups (D-026) and S3 keep the rest.

**Consequences:** local backups (`openlens backup`) hold only the days on disk; S3 holds the rest. Restoring a backup without the S3 bucket loses the cold days. Queries on raw events never read cold days; investigations further back (#325) will bring them back on demand.

## D-032 (2026-11-25, agent for #417, owner's delegation) The cold tier is an explicit opt-in, guarded by the bucket's lifecycle

**Decision:** D-031's move to S3 no longer starts because S3 is configured. It is **off by default** and turned on in *Storage and backups* (or `OPENLENS_S3_COLD=on`, which wins). Installs that already have cold days keep reading, erasing and expiring them; only new moves stop until the owner opts in. Before each pass, OpenLens reads the bucket's lifecycle rules and moves nothing when an enabled rule expires objects in under 400 days (the retention), whatever the rule's prefix, or when the rules cannot be read (fail closed). The reason shows on the Storage page and as `openlens_cold_tier_blocked` in `/metrics`. There is no override for a short lifecycle (minimal config).

**Why:** the tier deletes local data. An operator who set S3 up as a second copy, as D-016 promised, must not lose days to a backup bucket's 30-day expiration rule without a warning.

**Consequences:** a **breaking change** for installs that relied on the implicit move since v0.3.0 (announced in the 0.5.0 notes). A bucket with no lifecycle rule is accepted. The check reads `GetBucketLifecycleConfiguration`, so the S3 key needs that permission when the tier is on.


## D-033 (2026-11-25, agent for #444) The query budget follows the container, with no setting

**Decision:** the query memory pool is the process's memory limit minus 256 MiB, at least 256 MiB. The limit is read at startup from cgroup v2 (the smallest `memory.max` of the process's own cgroup, found in `/proc/self/cgroup`, and its ancestors: a container limit or a systemd `MemoryMax=` alike), else cgroup v1 (`memory.limit_in_bytes`), else `MemTotal` in `/proc/meminfo`; a limit of `max`, unreadable, or above physical memory counts as physical memory. When nothing can be read, the pool stays at 768 MiB. Each query uses as many partitions as the query runtime has threads (the CPUs the process may use, quota included, from 1 to 8), instead of 2. The startup log says what was chosen (`query limits from the host`). Background rollups wait until no board is being computed, one closed day at a time, and boards asked for meanwhile wait for that day to finish.

**Why:** with a fixed 768 MiB pool, memory beyond 1 GiB never helped the board (it failed at 2 M realistic events with 7 GB free), and on a 512 MiB container the pool was larger than the container, so the kernel killed the process before DataFusion could spill. A rollup pass running beside a board split the same pool and made the board fail at a third of its usual size. Following the container keeps D-014's promise (no tuning variable) while making "give it more memory" actually work.

**Consequences:** no new variable; if the detection is wrong, the detection is fixed. Under the Helm chart's default 1 GiB limit, the pool is 768 MiB as before. The [architecture challenge](https://github.com/Philippe-arnd/OpenLens/issues/442) measures the effect with the realistic profile of `xtask bench-gen` (#443).

## D-034 (2026-11-25, agent for #410) Environments: host rules on the server, and an unknown host is not production

**Decision:** amends D-012. A project holds **host rules** (an exact host or `*.suffix`, mapped to an environment or to `ignore`, at most 200), stored as a project setting and applied at ingestion to the host of the event's page address. The precedence order:
1. An environment the app set itself (it differs from what the SDK's hostname patterns give for that host) wins.
2. A host rule. `ignore` drops the event.
3. A hostname pattern of D-012.
4. Otherwise `unknown`, not `production`. It is kept apart and counted in no production number.

The browser SDK's patterns are ported to Rust (`openlens_event::detected_environment`), so the server tells a detected environment from a chosen one without an SDK change. Events with no page address (server SDKs) keep what they sent. Rules apply to new events only. **On upgrade**, once per project and in the background, every host that sent production events in the last 30 days gets a `production` rule. Until that has run, unclassified hosts keep what they sent.

**Why:** a staging host that no pattern matched (`kanban-test.example.com`, a preview URL, a bare IP) was counted as production and skewed the real numbers. The fix is one place to say which host is which, with no redeploy of the app. A guessed `production` should not count.

**Consequences:** a behaviour change for new hosts. An app that sets `init({ environment: "production" })` explicitly on a host no pattern matches looks the same as a guess, so a new host of that app is `unknown` until it gets a rule. Hosts seen before the upgrade are covered by the seed. No new setting or variable: the rules are project data, changed through `PATCH /api/projects/{id}`, `openlens-cli env` and the MCP `environments` tool. Re-labelling past days, an allow-list of hosts, per-environment uptime and alert levels, aliases and the settings card are follow-ups of #410.

**Amendment (2026-11-26, agent for #410, parts 3 and 4, and the SDK fallback):**
- **The browser SDK says `unknown`** for a host no pattern matches, instead of `production`. Step 1 above changes accordingly: for such a host, a received `production` (older SDKs) and a received `unknown` (this SDK) both count as detected, so the host rules decide for either, and old SDKs keep working. Before a project's upgrade seed has run, a detected `unknown` is stored as `production`, so the promise that an upgrade moves no host out of production holds for new SDKs too.
- **Aliases** (at most 50): an environment name the app sends (after the built-in folding of `prod`, `stage`, `dev`, …) is stored as another name, or dropped with `ignore`. They apply last at ingestion, to the name the app sent or the one a host rule gave, and only to new events: query-time aliases would apply twice with the folding and are not added. Production is never an alias source, and an alias never points to another alias, so one step always ends it.
- **Hidden environments** (at most 50): still stored and readable by name (`?env=`, SQL, the API), but left out of the environment selector of every page and of the board's environment list, except the one being viewed. Production, the default view, cannot be hidden.
- **Checks per environment** (at most 20): a non-production environment can get its own address, probed every minute with the project's health path and checked daily for TLS expiry, under the project's existing alert switches. Its incidents are `env:<env>:down|cert|cert_expired`, and its probes are kept in memory, apart from production's uptime history. Its **alert level** is `log` (the default: recorded on Uptime, never sent) or `notify` (announced on the project's channels like production's). Production keeps the app address and every alert, as before.
- **Re-labelling past events** (#484): the engine command `relabel_environment` moves the events of one host (exact or `*.suffix`) over the last N UTC days (default 30, at most 90, today included) to the environment a newly detected event of that host gets from the current rules and aliases. Once stored, an environment the app set itself cannot be told from one a rule gave, so it moves too, except `bot`; a host the rules `ignore` keeps its events (re-labelling never deletes). It goes through the erasure's file rewrite under the maintenance lock, after a flush; a closed day it rewrites loses its rollup, which the next pass computes again from the events, and the project's board cache is dropped. A dry run counts the moves per (old, new) environment and writes nothing; a rewrite is audited as `environments.relabel`. Exposed as `POST /api/projects/{id}/environments` (admin scope, like rule changes), `openlens-cli env relabel <host> [--days N] [--dry-run]`, the MCP `environments` tool (`relabel`, a dry run unless `dry_run` is false) and *Settings → Environments* (a preview, then a confirm button). No setting.
- All of it lives in the same project setting (`project:<id>:environments`, JSON `{rules, aliases, hidden, monitors}`), checked on write and on read, cached with the rules, and changed through the same engine commands (`set_environment_alias`, `remove_environment_alias`, `hide_environment`, `set_environment_monitor`, `remove_environment_monitor`), used by `PATCH /api/projects/{id}`, `openlens-cli env alias|unalias|hide|show|monitor|unmonitor`, the MCP tool `environments` and *Settings → Environments*. No new setting or variable beyond this project data.

## D-035 (2026-11-26, agent for #327) Replay sampling: about 300 recordings a day, no setting

**Decision:** no `OPENLENS_REPLAY_RATE` and no project setting. The share of sessions recorded from their start is `min(1, 300 / yesterday's active users)`, where active users are the distinct people with events on the project's yesterday (its time zone, D-017) in production, the team's own users included. The server counts it at most once a day per project (one query, kept in memory; a failed count keeps the previous rate and is retried after 10 minutes) and hands it to the SDK in the `GET /flags` response it already loads (`replay_rate`); no new endpoint. With no data yet, the rate is 1. The SDK draws once per session and stores the draw with the session, so all its tabs agree. A session left out still runs the recorder, but keeps the events in memory only: a full snapshot every 60 s, and only the events since the snapshot before the latest one (one to two minutes, at most about 1 MB). An `$error` the SDK captures or a rage click (`$rage`) sends that buffer and records the rest of the session as if drawn; another tab of the session follows within 10 s. A "churn signal" is not defined in the SDK, so it is not a trigger. Withdrawing consent empties the buffer, and the idle and hidden pause (#404) applies to buffering too. The replay page states the rate and why, read through the engine command `replay_rate`.

**Why:** storage and ingestion grew with traffic while nobody watches thousands of replays a day. A fixed daily budget keeps small apps fully recorded and large ones affordable, and the sessions that matter most (an error, a rage click) are kept with the minute before them. A rate knob would be one more thing to tune (D-014); if the budget is wrong, the budget is changed.

**Consequences:** above 300 active users a day, most sessions have no recording and the player's error and churn links find fewer replays. A recording sent after a trigger starts mid-session (its first chunk arrives late, with a chunk number taken then): the list and the player take its first event as its start, and the player's timeline leaves out session events from before it. Unsampled clients still pay rrweb's DOM observation. Dropping recordings under 5 s is not part of this.


## D-036 (2026-11-26, agent for #450) Identity is kept at ingestion, with dense integer person ids

**Decision:** every stored `$identify` is recorded in the metadata store (SQLite) before its batch is written: `person_aliases(project, anon, person)` with the rule the query layer applied to the files (an anonymous id identified as several users counts as the smallest one; an id is never its own alias; the `$anon_distinct_id` value is read exactly as before, 1 to 200 characters), and `person_ids(project, person, id, first_seen, internal)`, where `first_seen` is the earliest `$identify` (event time, not capture time) and `internal` once set stays set. Capture and import record the same way. The query engine reads these two tables (still at most every 30 s per project) instead of scanning every `$identify` with a regular expression. The existing `persons` table (role, account, plan; D-009) is left as it is: its `first_seen` is the first identify received, not the earliest one, a different meaning. Ids come from a per-project counter, start at 1 and are **never reused**, not even after an erasure, so a stored set of ids (ARCH-18) never points at someone else; "dense" means small and increasing, with gaps after erasures. **On upgrade**, each project's tables are filled once from its files, in the background (at startup, one project after another, and on the first batch of a project not yet done; a failure is retried ten minutes later). Until a project's fill has finished, the engine keeps deriving identity from the files, so results never depend on it. Erasure deletes the person's id row and every alias to or from the erased ids; a fill that read the files before an erasure does not bring them back.

**Why:** the alias and person tables were recomputed every 30 s by reading every `$identify` of a project's whole history, the largest fixed cost of a board after a cache miss, and compact per-person sets need integer ids. The rule is unchanged, so results stay the same.

**Consequences:** identity now outlives the events it came from, like the `persons` rows already did: after retention or the cold tier removes an old `$identify`, its anonymous id still counts as the user, and their `first_seen` stays their real first visit. No new setting or variable. The tables are SQLite rows next to `persons`, in the same backup.

## D-037 (2026-11-26, agent for #449) Web Vitals facts are stored as typed columns; old files are read through the text

**Decision:** the event files gain nullable columns, appended after `properties`: `vital_name`, `vital_device`, `vital_el`, `vital_kind`, `vital_res` (text) and `vital_value`, `vital_ttfb`, `vital_load_delay`, `vital_load_time`, `vital_render_delay`, `vital_input_delay`, `vital_processing`, `vital_presentation` (double). They are set only on `$vital` rows with a valid `$name` (`[A-Z]+`), computed from the stored `properties` when a segment is written. Each value is kept only where the regular expression the engine used on the text would have found it (same character classes and length caps: `$el` 1–120 characters, `$res` 1–200, `$el_type`/`$input` `[a-z]{1,12}`, `$device` one of three, numbers only when JSON numbers), so the rule is the old one, applied once. `properties` is unchanged. Files written before have no such columns and are **not rewritten** (D-024): the `events` view reads each column as `CASE WHEN event = '$vital' AND vital_name IS NULL THEN <the old expression> ELSE <column> END`, and compaction, erasure and click trimming fill the columns in from `properties` when they rewrite a file. The board's 90-day snapshot drops `properties`; Web Vitals get their own snapshot of 7 days of `$vital` rows and the typed columns. Scope is the narrow one: identity (`$anon_distinct_id`, `$internal`) left the per-query path with D-036; errors (`$message`, `$source`, `$stack`), acquisition (`$channel`, UTM) and churn's `$rating`/`$rage` are not on the board path and keep reading the text for now.

**Why:** the board ran two regular expressions per `$vital` row and kept `properties`, most of an event's bytes, in its snapshot for them; the attribution of #467 added eleven more per row. Matching the old patterns exactly keeps old and new files giving the same answers.

**Consequences:** a new segment is a little larger (thirteen mostly-null columns, a few bytes per `$vital`). Changing what a column holds now needs a new column, not a new regular expression. No new setting.

## D-038 (2026-11-26, agent for #451) A daily per-person rollup, keyed by the person's id as text, features resolved when the day closes

**Decision:** each closed UTC day gains a sixth rollup table, `person_day` (`rollups/v1/project=<p>/date=<day>/person_day.parquet`): one row per person, environment, release, role and feature of the day, with `events`, `sessions`, `errors`, `successes` (task events, as the board counts them: the map's success events, or any event with a feature when the map declares none), `first_ts`, `last_ts` and `map_version`. The day is the directory, as for the other tables. The person is the merged person of every query (anonymous visits identified later count as the user), stored as **text**, not as the integer id of D-036: anonymous visitors have no id, the board counts them on their own, and "identified" is decided when reading (`persons`), so an integer column would either drop them or need a second key; Parquet's dictionary encoding already stores each person once per file. The role is the raw one the event carried, as in `person_q` and `metric_q`, so the map's role rules apply on reading. The **feature is resolved with the feature map in force when the day is rolled up** (the same lookup as the board, #446), because a map can define a feature by route or success event, which no per-person row could resolve later without keeping every path; `map_version` records which map that was (null without a map). Adding the table makes every older day that still has its events "not rolled up" again: the background pass (seven days per project every ten minutes, D-025) computes **only the tables a day lacks**, so the other five files are left as written (recomputing `click_q` or `label_q` after a day's click details were trimmed, D-028, would lose them). Erasure removes the person's rows from `person_day` exactly as from `person_q` (D-026): a day with its events is rolled up again, an older day loses their rows.

**Why:** active people per feature, role, week or month went back to the events, because `person_q` has no feature and `metric_q` counts distinct people per bucket, which do not add up across days (#451). A per-person, per-day row adds up: distinct people over any set of days is a distinct count over these rows. Keeping the text id keeps erasure the same filter as before and adds no new personal-data file.

**Consequences:** the table is not read by the board yet (#452). Days past the raw retention, or already moved to the cold tier, have no events to roll up and never get the table: a reader must treat a missing `person_day` as "not available" for that day. A feature map change does not re-roll closed days: their `map_version` tells a reader which days were resolved with an older map. Until an older day has been rolled up again, its click details are not trimmed (`trim_clicks` waits for every table) and the cold tier does not take it, a delay of hours on a long history. Integer ids, bitmaps and days in the project's zone (rows are per UTC day; `person_q` keeps the 15-minute buckets) are left for when the board's measurements call for them. No new setting.

## D-039 (2026-11-26, agent for #482) Error, acquisition and friction facts are typed columns too, with a version on every row

**Decision:** the rule of D-037 is applied to the facts it left on the text. The event files gain, after the Web Vitals columns, the nullable text columns `vital_rating` (`$rating` of a `$vital`, `[a-z]{1,12}`, even without a valid `$name`), `error_message`, `error_source`, `error_stack` (of an `$error`), `acq_channel`, `acq_utm_source`, `acq_utm_campaign`, `acq_ref_host` (of a `$pageview`), the boolean `click_rage` (of a `$click`: `$rage` is `true`; false otherwise) and the integer `facts_version`, set to 2 on **every** row written since. Each value is what the old expression returned, read once at write time from the parsed `properties`: `$message` and `$stack` as spelled in the JSON text (escapes included, which is what the fingerprint masks and what serde_json writes back for the parsed string), `$source` as spelled up to its first `"` (`([^"]*)`), the landing keys as spelled up to the first `"` and only when that is 1 to 200 characters (`([^"]{1,200})`), `click_rage` exactly `LIKE '%"$rage":true%'` for a top-level key. A page view carrying none of the landing keys, and a click without `"$rage":true` in its text, are not parsed. Files written before have no such columns and are not rewritten (D-024): the `events` view reads each one as `CASE WHEN facts_version IS NULL AND event = '<its event>' THEN <the old expression> ELSE <column> END`, and compaction, erasure and click trimming fill them in. The error groups, a feature's errors, the acquisition table (which now keeps landings with `acq_channel IS NOT NULL` instead of the text containing `"$channel"`, the same landings minus those it skipped anyway) and churn's friction read only the columns. Other per-row patterns (click coordinates and labels, scroll depth, forms, surveys, revenue, explore's dimensions, the rollups' clicks) stay on the text: moving one column of a query that still reads `properties` saves nothing.

**Why:** these queries were the last ones on the main pages to run a regular expression per row over `properties`, most of an event's bytes. D-037's marker (`vital_name IS NULL`) only works because every vital has a name; an error without a message or a page view without a channel would run the old expression on every new row, so a version column says which rows were written with the facts, at the cost of one constant column per file (a few bytes once compressed).

**Consequences:** only top-level keys count, as the SDK and the server write them; a key nested in an object, which the old pattern could find first, is not read. A later set of typed facts raises `facts_version` and tests it the same way. No new setting.

## D-040 (2026-11-27, agent for #492) The board's people blocks combine `person_day` for closed days with the events for the rest

**Decision:** the board's users (DAU, WAU, MAU), known, anonymous, roles, role × feature, features and daily active series count people from one row per person, environment, release, role, feature and UTC day. For each day of a block's window, the row comes from `person_day` (D-038) when the day is closed (D-025), lies entirely after the day the window starts in, has the table, and every row of the day carries the `map_version` in force (or none, on both sides, without a map); otherwise it is the events of that day, grouped the same way and cut at the window's start as before. Days never come from both, so a person is counted once. The role is the raw one the rollup stored, mapped on reading by the same rules as the events (the map's role function), and "identified or anonymous" is decided at read time from `persons`, as today. A rolling sub-window (DAU's 24 hours, WAU's 7 days inside the 30-day rows) counts a person whose row's `last_ts` falls inside it, which is exact because a row's last event is its latest. Rollup rows are UTC days: a block that groups by the project's day (the daily series, the features' user-days) reads them only when the project's zone has a zero offset at every midnight of the window (UTC, or for example London in winter); otherwise that block stays on the events, the others still use the rollup. A day rolled up with an older map is read from its events, so a map change is honoured without re-rolling closed days (#489, items 1 and 2), as long as the events of that day are still kept; a day with neither its events nor a matching rollup, such as one past retention or in the cold tier, counts nobody, as before. The sessions, releases, success and Web Vitals blocks, and the insights, journeys, cohorts, funnels, task times, resurrected users and retention, still read the 90-day snapshot, which stays until every block is moved (#452).

**Why:** distinct people over days add up from per-person, per-day rows (D-038), so closed days no longer need their events while the board's numbers stay those of the events, within the gap D-025 already accepts (aliases arriving after a day is rolled up). Falling back to the events for a day rolled with another map is cheaper and simpler than re-rolling every closed day on each map push, and it keeps the feature lookup of the map in force. Converting UTC rows to another zone's days would need the hour of each event, which `person_day` does not keep.

**Consequences:** in a zone off UTC, the daily series and the features block keep reading the events. After a map change, the people blocks read the events of every closed day until the days are rolled up again, which happens only when a table is missing or after an erasure (D-038); re-rolling on a map change, or treating days past retention differently, is left to #489. No new setting.

## D-041 (2026-11-26, agent for #493) A daily per-session rollup, re-assembled across midnight on reading

**Decision:** each closed UTC day gains a seventh rollup table, `session_day` (`rollups/v1/project=<p>/date=<day>/session_day.parquet`): one row per session, person, environment, release and role of the day, with `first_ts`, `last_ts`, `interactions` (events done on purpose: the board's bounce rule, now `openlens_query::INTERACTION`, which the engine's copy is tested against), `errors` (`$error` events), `tasks` (counted as `person_day` counts successes, D-038) and `map_version`. Events without a session are left out, as the board leaves them out. The person is the merged person and the role the raw one, as in `person_day`. The person, environment, release and role are part of the key, not values picked per session, so a row is in practice one session, and a filter on any of them selects exactly the events the board's filter selects (a session over a deploy has one row per release, as the releases table counts it). A session crossing UTC midnight has a row on each day; a reader re-assembles it by `session_id` with `min(first_ts)`, `max(last_ts)` and the sums, which gives the board's session count, duration, bounce and error flags and tasks exactly. Like `person_day`, the background pass adds the table to older days that still have their events without rewriting the other six, and erasure removes the person's rows (a day with events is rolled up again, an older day loses their rows). This amends D-026: rollups now hold session ids (random ids the SDK makes, never a URL or property), kept as long as the project, and removed with the person.

**Why:** the sessions and releases blocks of the board need per-session facts (duration, bounce, errors) that neither `person_q` nor `person_day` can give, and option A of #452 keeps their definitions exact instead of approximating them. Keying by session and its dimensions keeps the table additive across days and filters, with rows about as many as sessions.

**Consequences:** the board does not read the table yet (#452). Days without events (past retention, cold tier) never get it, so a reader treats a missing `session_day` as not available. A feature-map change does not re-roll closed days; `map_version` says which map decided the tasks. The session's day for "user days" (the board's `min(day)` in the project's zone) is rebuilt from `first_ts`. No new setting.

## D-042 (2026-11-26, agent for #494) Commands live in the engine, with a registry and an access level each

**Decision:** actions are typed commands in `crates/engine` as `openlens_engine::commands` (option A of #308): no new crate and no change to the layers. A command implements `Command`: a stable `area.verb` name, a serde input and output, an access level and an async `run` against a `Host`, the trait through which the process that runs it (today the server) gives the metadata store, the query engine, a project, its feature map, its cached board and its timeline. The levels are those of the server's typed access checks (#294, `crates/server/src/access.rs`): `Read` (anyone signed in who may see the project), `Write` (`ProjectWrite`: an admin who may see the project, or the bearer token) and `Admin` (an admin of every project, or the bearer token). A command declares its level; it does not check it: the adapter does, with the extractor it already used, so no request is authorised differently. `REGISTRY` lists every command as a name and a level, the one list a front end or a test enumerates; there is no dispatch by name. MCP stays an HTTP client of the REST API (D-020). Goals and objectives are the first commands (`goals.list`, `goals.set`, `goals.delete`, `goals.set_objective`, `goals.delete_objective`), moved from `crates/server/src/goals.rs` with no change of behaviour: the page, form, REST and Ask handlers there now build an input, run the command and render its output; audit entries and redirects stay in the adapters. The hourly pass is two engine functions (`guard_checks`, `close_periods`) rather than a command: nobody calls it, it is a schedule.

**Why:** rule 10 says every action is an engine command, but goals' logic and storage sat in the server, reached by different paths from the page, the API and Ask. A registry is what lets a test compare the commands with the MCP tools; declaring the level next to the command, while the adapters keep checking it as before, keeps this a move (rule 7).

**Consequences:** `openlens-engine` now depends on `openlens-meta` (L1) for the stores. The goal row types the Goals page renders are the engine's (`openlens_ui` re-exports them). Later parts of #308 move alerts, tickets, explore, Ask's tools and the remaining SQL the same way, then add the parity test between `REGISTRY` and the tools of `openlens-cli mcp`, which does not exist yet: until then the registry test only checks that names are unique and well formed. No new setting.

## D-043 (2026-11-26, agent for #485) A host allow-list that cannot lock out ingestion

**Decision:** a project may hold a **host allow-list** (at most 50 exact hosts or `*.suffix`, the patterns of D-034's rules), stored in the same project setting as the rules (`allow` in `project:<id>:environments`). Events whose page address is on another host are dropped at ingestion, before the host rules. Four guards keep a mistyped list from locking the app out:
1. **A preview before every save.** The engine command `preview_allowed_hosts` reads the last 7 days of stored events per host and gives, over the last 24 h, the hosts outside the list with their event counts, the events kept (listed hosts, and events without a page address), and whether the list would be active. The API (`POST /api/projects/{id}/environments/allow`, admin scope) only previews unless `confirm` is true, and a confirmed save returns the same preview; the settings tab shows it and a *Save the list* button under it; the CLI (`env allow <hosts…>`) and the MCP `environments` tool (`allow`) preview unless told to confirm.
2. **Pending until a listed host proves it.** The list drops events only while a host on it has sent events in the last 7 days. Until then it is *pending* and drops nothing, and the tab says so. A list that names no real host never drops anything, and a list left behind after a move to a new domain lets the new one in again a week after the old one went quiet. Ingestion learns when a listed host last sent events from the batches themselves (a listed host in a batch activates the list for that batch), from the stored events read in the background the first time a server sees the project's list, and from the preview when the list is saved.
3. **Drops are counted and shown.** Ingestion counts dropped events per host in memory (at most 100 hosts one by one, the rest together), shown in the tab, in `GET /api/projects/{id}/environments` (`allow`) and in the MCP result. The counts start again at a restart, a change of the list, or after eight days without a batch.
4. **Off by default, never for server SDKs.** An empty list is off. Events with no page address (server SDKs, imports) are never dropped.

Changing the list is the engine command `set_allowed_hosts`, audited as `environments.allow` with the list and its preview's numbers.

**Why:** a project's capture key is public (it is in the page), so anyone can send events under it from another site. An allow-list stops that, but a list that is wrong by one letter would silently drop every real event, which is worse than the problem. Making the list prove itself with real traffic before it acts, and showing what it drops, turns a typo into a visible *pending* status instead of lost data.

**Consequences:** events dropped by the list are gone, not stored aside; the preview and the counts are the only trace. A list becomes active on the first batch from a listed host, so after a restart or a change other hosts' events pass until then. A pending list does not protect anything, by design. No new setting or variable: the list is project data like the rules.

## D-044 (2026-11-26, agent for #495) Automatic release names from a build fingerprint, kept in a small table; stored events are not renamed

**Decision:** the browser SDK sends `$build`: FNV-1a (32 bits, 8 hex characters) of the sorted, de-duplicated script `src` and stylesheet `href` URLs of the page's own origin (path and query; other origins and OpenLens's own `c.js`, `r.js`, `s.js` left out), computed once per page load in `init`. It stays in `properties`. At ingestion, an event with no `$release` but a valid `$build` (1 to 64 letters, digits, `-`, `_`) gets the name recorded for that fingerprint in the project and environment, in the metadata table `release_builds`. A fingerprint seen for the first time is named `YYYY-MM-DD.N`: the day of its arrival in the project's time zone, N its order among that day's automatic names in that environment. An explicit release always wins; arriving with a fingerprint, it becomes that fingerprint's name (an alias), so later events of the same build without a release get it. Bots get nothing. Bounds, fixed: at most 50 new fingerprints per project and day (past it, events of a new fingerprint keep no release), and 500 per project (oldest first out). Names are cached an hour per fingerprint, so a known build costs no metadata read; a new one costs one read and one short write. The Node SDK's `release` defaults to the host's commit variable (`SOURCE_COMMIT`, `GITHUB_SHA`, `VERCEL_GIT_COMMIT_SHA`, `CF_PAGES_COMMIT_SHA`, `RENDER_GIT_COMMIT`, `HEROKU_SLUG_COMMIT`, in that order; a full hash shortened to 12 characters), then `npm_package_version`; an explicit `release` wins. The browser SDK also reads `<meta name="release">` after `openlens-release`.

**Why:** most apps never pass a release, and their builds already change file names on every deploy, so a fingerprint finds releases with no integration (#237, layer 1). The name is set at ingestion, so every query, rollup and share link keeps reading a plain `release` column.

**Consequences:** past events are **not rewritten** (D-024): events stored under an automatic name before an alias keep it, so one build may show under its automatic and its explicit name until it is superseded. Resolving aliases at query time, or renaming at compaction, is left to the release lifecycle work of #237. The same build in staging then in production gets a name in each environment. No new setting.

**Consequences:** "only real breakage reaches a person" is not met yet: a person still merges each fix, but no longer diagnoses it. ## D-047 (2026-11-27, agent for #498) The board's sessions and releases combine `session_day` for closed days with the events for the rest

**Decision:** the board's sessions block (count, average duration, bounce rate, error rate, tasks per user-day) and its releases table read one row per session, person, release and UTC day, with that day's first and last time, interactions, errors and tasks. A day's rows come from `session_day` (D-041) under the people blocks' rule (D-040, the same code): closed, entirely after the day the window starts in, rolled up, and every row of the day with the `map_version` in force; otherwise from the events of that day, grouped the same way and cut at the window's start. The rollup's raw role is mapped on reading and the filters (environment, role, release, internal people) apply to its columns as to the events. The rows are then put back together per session exactly as the old queries grouped the events: by `session_id` alone for the sessions block (first person `min(distinct_id)`), by release and `session_id` for the releases table (whose window still ignores the release filter), with `min(first_ts)`, `max(last_ts)` and the sums, before the same aggregates. A session crossing midnight, including from a rolled day into an open one, is therefore one session. A session's day for user-days is the project-zone day of its first event, taken from `min(first_ts)`, so unlike the daily series and features of D-040 these blocks use the rollup in every zone. The engine's copy of the interaction rule is gone: the board uses `openlens_query::INTERACTION`, the rule `session_day` is rolled with. Success events and Web Vitals still read the snapshot.

**Why:** `session_day` keeps each session's first and last instant, so the project's day of a session needs no event hours, which `person_day` lacks; re-assembling before aggregating keeps the definitions of the two blocks, which differ only in their grouping. Sharing the per-day choice with the people blocks means a map change, a missing table or a day past retention is handled once.

**Consequences:** a session's day is the zone's day of its earliest instant, which equals the earliest event's day except in a zone whose clock goes back across midnight, where the two may differ by one day for a session spanning that change. A day whose `session_day` was rolled with an older map is read from its events, like `person_day`. No new setting.

## D-049 (2026-11-26, agent for #500) Release states from the share of daily users; time in staging from the name or the build fingerprint

**Decision:** the Releases page, `GET /api/projects/{id}/releases` and the MCP `releases` tool run one engine command, `releases.list` (`Read`), over the last 90 days of events with a release (bots and events with no release left out; one query per (environment, release) and one per (environment, release, day), typed columns only, at most 500 releases and 20 000 daily rows). A release's **share** on a day is its distinct users that day over the sum of every release's distinct users that day in the same environment (users, not events, so one busy user does not move it; a user seen on two releases counts in both, so the shares add up to 100 %). Days are the viewer's or the project's (D-017). Releases are ordered by their first event in the environment. **Majority** is more than half. The state is read on the environment's latest day with data: after the last day the release held the majority (or since it appeared, if it never did), the last release to hold the majority decides: an older one makes it **rolled back** (only for a release that had the majority; a canary next to an older majority keeps rolling out), a newer one **superseded**. Otherwise it is **live** when it has at least 95 % of the latest day's users, or when it reached 95 % before and still holds the majority (a canary of the next release does not demote it), and **rolling out** otherwise. **Time in staging**, for a production release: from the first `staging` event of the same release name, or of a name one of its build fingerprints had in staging (`release_builds`, D-044), to its first production event, when that came first. The internal team's users count: staging traffic is mostly theirs. The page lists every environment, production first, newest first, with a link to the board filtered on the release and environment.

**Why:** the states and the promotion are read from traffic the server already stores, with no deploy hook, which comes later in #237. Daily shares are cheap (two grouped queries over partition-pruned typed columns) and stable against a busy hour.

**Consequences:** a release first seen more than 90 days ago is ordered by its first event in the window. A build named automatically then explicitly (D-044) still shows under both names. A pulled canary stays *rolling out* until a newer release takes the majority. Only the environment named `staging` counts as staging. No new setting.

## D-050 (2026-11-26, agent for #487) Self-hosting part 2: install.sh delegates to openlens-update, no in-binary updater, Nomad pinned by digest, NixOS built from source

**Decision:** `deploy/systemd/install.sh` is a POSIX `sh` bootstrap for the binary + systemd path. It checks the machine and the tools, resolves the channel (`latest` or `X.Y`; without one, the minor of the newest stable release), downloads `openlens-update` and the three units **from the git tag of the release it installs**, creates the user and a root-only env file (with `OPENLENS_PUBLIC_URL` when it is set in its environment), then runs `openlens-update <channel>`, which does the checksum and build-provenance checks and the rollback. It does not verify the release itself: one verifier, in `openlens-update`, is used for the install and every update. It enables the daily `openlens-update@<channel>.timer`, since a minor channel only brings patches, and installs no package (it says what is missing). Releases before 0.6.0 are refused, as by `openlens-update`. An in-binary `openlens update` is not added: `openlens-update` already covers the systemd path with verification and rollback, and the image paths are updated by their orchestrator. The Nomad job runs one allocation on a host volume, with an `update` block without canaries (the old allocation stops first) and `auto_revert`; since Nomad does not look at a tag again, `openlens-nomad-update` resolves the channel tag to its digest on GHCR and runs the job with `-var image=…@digest`, so the same digest is no change and a new one is a new job version that Nomad reverts on failure. The NixOS module `services.openlens` mirrors `deploy/systemd/openlens.service` and only exposes `enable`, `package`, `address`, `publicUrl` (the existing `OPENLENS_ADDR` and `OPENLENS_PUBLIC_URL`) and `environmentFile`; other variables go through `systemd.services.openlens.environment`. Its package is built from source with `cargoLock.lockFile` (every dependency is on crates.io), so no hash changes per release; `flake.nix` sits at the repository root and pins `nixos-25.11` (Rust 1.88). Panels: a CapRover one-click template and an Unraid template (running as `99:100`, the owner of `appdata`) are files; Dokploy, Dokku, Portainer and TrueNAS are recipes over the one image. YunoHost is left out: it needs an app package of its own.

**Why:** two verifiers in two shells would drift; fetching the units from the release's tag keeps them in step with the binary and gives them the same trust as `install.sh` itself (HTTPS from GitHub). A digest in the job is the only way Nomad sees a new image as a change it can roll out and revert. Building from source with the lock file avoids per-release hash bumps that nobody could check without Nix.

**Consequences:** the systemd files fetched by `install.sh` are not themselves signed; signing them would mean attaching them to the release assets (a CI change). The Nomad job, the NixOS module and flake and the panel recipes were written from public documentation and are not validated with `nomad`, `nix` or the panels here; CI tests are #486. The flake and module must be in a release tag before the `github:Philippe-arnd/OpenLens/v0.6.0` examples work. No new setting.

## D-051 (2026-11-27, agent for #502) The board holds no copy of the events: success events and Web Vitals are bounded scans, and boards are no longer capped at two

**Decision:** the board no longer builds a 90-day snapshot of the projected events, nor the 7-day one of `$vital` rows; `BOARD_SNAPSHOT_ROWS`, `QueryEngine::snapshot` and `shared_snapshot` (#418), the board-snapshot metric and the server's `PARALLEL = 2` are removed. Every board query reads its source directly, cut to its own window of days (`date` partitions) and to the columns it names: the people, sessions and releases blocks combine the daily rollups with the events as in D-040 and D-047; success events are a 30-day scan with `event IN (the map's success events)` and Web Vitals their 7-day scan of `$vital` rows (option B of #452), both on typed columns only; the insight cards, journeys, flag cohorts, task times, resurrected users and retention read their 30- or 90-day window from the files, and funnels only their steps' events. No query keeps a result between queries: what a query holds is its own working memory in the shared pool (D-033), which spills or fails that query alone. Boards of different filters are therefore computed side by side, without a cap; a background rollup pass still waits until no board is being computed, and boards asked for meanwhile wait for its day (#444), now through a read-write lock instead of the two-permit semaphore.

**Why:** the snapshot made the board's memory grow with the events of the window (about 160 bytes each, D-023) and was the only large thing a board held; `PARALLEL` existed to bound how many snapshots lived at once. With closed days from rollups (D-040, D-047) and the two remaining raw reads narrowed to a few event names over 30 and 7 days, a copy no longer pays for itself, and reading the files once per query is what the board already did above 4 M events.

**Consequences:** the board's cost depends on the days and the events each query actually selects, not on a 90-day copy; the insight cards, journeys, cohorts, task times, resurrected users and retention still scan their window of events, which a later change can move to rollups. Boards that used to wait for a permit now run beside each other and share the query pool. The sizing docs no longer describe the 4 M cap; the `scale` job of `perf.yml` and the ARCH-10 scenario re-measure the time and memory, and the numbers are updated from there, not estimated. No new setting.

## D-053 (2026-11-26, agent for #504) A per-project deploy hook: one secret URL, formats told apart by shape, deploys tied to releases by name, commit or time

**Decision:** each project may have one deploy hook URL, `POST /hooks/deploy/<secret>`. The secret (`dh_` and 40 random letters and digits) is made or rotated by the engine command `deploys.rotate_hook` (`Write`), from the Releases page (an admin's *Make the URL* / *Rotate the URL*, the box ticked to rotate), `POST /api/projects/{id}/deploy-hook` (write scope) and the MCP `deploy_hook` tool; it is shown once, in that response (never in a redirect), and only its SHA-256 is stored, in `deploy_hooks` (one row per project), looked up by hash like API tokens and share links. Rotation is audited as `deploys.rotate_hook`. A wrong or unknown secret answers **404 with no body**, like a route that does not exist. The request log writes the path as `/hooks/deploy/<secret>`. The hook takes at most 256 KiB, 10 s, 1 request a second per client address (burst 30, before the secret is looked up) and 1 deploy every 10 s per project (burst 30), with the capture limiter's token buckets; a 429 says to retry in a minute. The format is told by a header when the platform sends one (`X-GitHub-Event: deployment_status`, Flux's `Gotk-Component`), otherwise by the body's shape, in this order: Flux (`involvedObject` and `reportingController`), Vercel (`type` `deployment.*` and `payload`), Render (`data.serviceId`), Coolify (`event` `deployment_*` with an application or deployment id), Netlify (`site_id` and `state`), Argo CD (`phase`, or `app` as an object: the template given in `docs/agents/wire.md`, or `{{toJson .app}}`), Fly (`FLY_APP_NAME` or `FLY_IMAGE_REF`, since Fly sends no deploy notification: a step after `fly deploy` posts them, and the image tag is the release), then the plain form `{status, release?, commit?, environment?, at?}`. Each gives a status: *started*, *succeeded*, *failed* (canceled counts as failed) or *rolled back*; notifications of those platforms that are not deploy steps (a ping, a build event, an inactive state) answer 202 and record nothing; an unknown shape answers 400 with the accepted forms. The environment is the hook's `?env=` first (for Render and Fly), then the notification's, normalised like events' (Vercel's and Netlify's previews are `preview`, Coolify's pull requests too), else `production`; a release is kept up to 200 characters, a commit only as 7 to 64 hex digits, and a time later than an hour from now becomes the arrival time. Deploys go through the engine command `deploys.record` into `deploys`, at most 500 per project (oldest first out); deleting a project removes both tables. `releases.list` reads the last 91 days of deploys and ties each to a release seen in its environment: by name; else by commit, when the release name and the commit are prefixes of one another with at least 7 characters (the Node SDK names a release after the commit, D-044); else, for a succeeded deploy that names neither (Coolify, Render), the first release first seen in the environment in the 2 hours after it and not tied already. A release gets `deployed_at` (its latest succeeded deploy) and `deploy` (the status of its latest deploy). A deploy tied to no release is listed on its own, with no users and no board link: **failed**, **rolled back**, or **deploying** (started or succeeded, no traffic yet); a start and its end under the same name are one row, and of the deploys that name nothing only the environment's latest still deploying is listed. The output also lists the deploys, newest first, and when the hook was set up. The URL lives on the Releases page, not in the project settings, because what it feeds shows there.

**Why:** a hook gives the deploy time and the failed deploys that traffic alone cannot (#237, layer 2), with one URL pasted once by the agent that wires the app. A secret in the path is what every one of these platforms can send (none of them signs the same way), so it must be unguessable, unlogged, stored hashed and not revealed by a different answer. Telling formats apart by shape needs no setting per platform. Tying by commit prefix reuses the names releases already have; tying by time covers the platforms that send no commit.

**Consequences:** the platforms' own signatures (Netlify's JWS, Render's and GitHub's HMAC) are not checked: the secret URL is the credential, so a leaked URL lets its holder record deploys until it is rotated, never read anything. Tying by time can pick the wrong release when two deploys land within two hours with no commit. A deploy older than 91 days, or of an environment with no release seen, is listed but tied to nothing. The Fly and Argo CD forms are ours (Fly has no notification, Argo CD's body is a template). The release states *failed* and *deploying* only come from the hook. No new setting: `?env=` is part of the URL the agent pastes.

**Decision:** the last SQL of `crates/server/src` outside Ask and explore moves to the engine as plain functions in `openlens_engine::reads`, with no change of behaviour: the feature map's last 7 days (`map_live`, its `MapLive` now the engine's and re-exported by `openlens_ui`), the anonymous ids linked to a person and a person's events (`linked_anonymous_ids`, `person_events`, for erasure and the right-of-access export), one day of events for the NDJSON export (`day_events`, with `is_day`), the settings checklist's counts of the last 24 hours (`day_counts`), the projects page's activity (`recent_activity`), the origin most page views came from (`top_page_origin`) and a session's markers on the replay timeline (`session_markers`). None is a command: each feeds a page, an export or a check, and forgetting and exporting a person stay server handlers because they also flush, rewrite files and fetch cold days back. `cargo xtask server-sql`, part of `cargo xtask ci`, fails on a Rust string literal in `crates/server/src` that reads like a query, in any case: `select` then `from` (unless `select` is followed by an article or a word like *your*, as in "Select a project from the list"), `insert into`, `update <name> set`, `delete from`, `with <name> as (`. Comments and `#[cfg(test)]` code are skipped (a test may send SQL to an endpoint). `ask.rs` and `explore.rs` are allowed while #507 and #508 move them, and an allowed file with no SQL left fails the check, so the list is emptied as they land. A unit test in `apps/openlens-cli/src/mcp_parity.rs` compares `commands::REGISTRY` with the tools of `openlens-cli mcp`: each command is mapped to the tool that runs it (`TOOL_OF`; names differ) or listed in `PENDING`, each tool runs a mapped command or is listed in `NOT_COMMANDS` (tools whose logic is not a command yet, and `sql`, the raw read-only escape hatch), and an entry naming nothing fails. `openlens-cli` gains `openlens-engine` as a dev-dependency (L6 on L3).

**Why:** rule 10 puts every query in the engine; a case-insensitive lint keeps it there, where a grep for `SELECT ` missed lowercase and multi-line queries (#308). The parity test turns "anything you can do in the UI, an agent can do through MCP" into a failing test when a command is added without a tool, while the lists say plainly what is not there yet.

**Consequences:** the lint reads string literals, so SQL built from small fragments ("FROM" in one literal, "SELECT" in another) would pass it; the engine is where such building belongs anyway. Ten commands have no tool yet (goal deletion and objectives, the five alert commands, `tickets.target`, and `deploys.record`, which the deploy hook runs, not an agent), and 26 tools are not commands yet. No new setting.
