# 🔭 OpenLens v0.7.0

**Your backend joins the picture, and each release reports on itself.** v0.7.0 reads the server side of your app (errors, routes, outgoing calls, jobs and runtime health, from the Node SDK or any OpenTelemetry exporter), reads each release's notes from GitHub and writes its verdict back there, and rebuilds the Focus board around the questions a product manager asks: is production fine, did the last release help, what is in flight, and which features people use.

## ⚠️ Upgrade now if…

- **You update with `openlens-compose-update` on Docker's containerd image store**. After a failed update it could not go back to the previous image; it now keeps that image under a local tag until the update is over. On Swarm, the guide's daily cron line left the service without a digest on Docker 29, so no new image ever arrived: use the new line, which deploys the stack again (#597).

## ✨ Highlights

- 🖥️ **Server errors from Node.** `captureException` sends a server exception as an error grouped, alerted on and judged per release like a browser error. Each group is tagged *Browser* or *Server*, and a server error lists the browser sessions that made the request, with their replays (#593, #624).
- 🛣️ **Route stats and a Routes tab.** The Node SDK counts every request per route and status in short windows, as OpenTelemetry's `http.server.request.duration` histogram, never one event per request. *Quality › Routes* shows requests, 5xx, p95 and their trend, key actions first. A route that breaks makes the release *regressed* and opens an incident (#594, #601, #622).
- 📡 **Already on OpenTelemetry? Point it at OpenLens.** `POST /v1/metrics` takes OTLP/HTTP metrics with the project key, so a Collector or an exporter sends route and dependency histograms with one header (#605).
- 🔎 **One real request behind a slow route.** Each route keeps its slowest request and its first 5xx, which open the replay at that moment or show the trace id. Never the user (#607, #629).
- 🔌 **Outgoing dependencies.** An opt-in `captureOutgoing()` counts the app's HTTP calls per external host. *Errors › Dependencies* shows which provider got slower or fails more, and a host failing for 15 minutes opens an incident. It is shown next to the verdict, never judged (#608, #630).
- ⏰ **Job check-ins.** A cron job checks in with one `curl`, or `checkIn` in every server SDK. OpenLens learns how often it runs and alerts once when a run is missed, fails or takes twice as long (#609).
- 🩺 **Runtime health per release**: restarts per day, memory and event-loop delay next to the release before. A crash loop makes the release *regressed* (#610, #631).
- 🧩 **The backend in the verdict.** The release verdict gets a Backend group (worse routes, new server errors, a broken key action first), and the Releases page lists the routes that got worse with sessions to replay (#623).
- 📝 **Release notes from GitHub.** For each release recorded with its commit range, an hourly pass reads the commits, pull requests and files, and shows them grouped Added, Fixed, Changed (#574).
- 🗂️ **Features touched by a release.** Features can list their code paths, and the verdict judges the features a release changed first (#576).
- ✍️ **The verdict written back to GitHub**: a commit status, a block in the GitHub release, a comment on each shipped pull request, and an issue when the release regressed (#575). See *Changes in behaviour*.
- ⏳ **Delivery numbers you can trust.** Lead time is measured from the first commit of the release (#633), and the change failure rate counts releases judged regressed (#611).
- 🎯 **A Focus board in the order of your questions** (UI v2.1): *Production right now* in one strip, a regressed release as the lead, five Outcomes tiles (reach, value, retention, quality, speed), an *In flight* card for goals, tickets and flags, and one Features table. The other blocks moved to the page that owns them, one click away (#614–#620, #623).
- 📈 **People › Retention**: the weekly cohorts and a survival curve, with one line on the board (#619).
- 💽 **Recordings follow the disk.** One disk budget raises the recordings kept a day from 300 up to 30,000 on a large disk, and picks finer route-stats windows when there is room. Retention stays fixed. *Settings › Storage* says what the disk allows and why (#606, #628, #632).

## 🚀 Install or upgrade

```sh
docker run -d -p 8686:8686 -v openlens-data:/data ghcr.io/philippe-arnd/openlens:0.7
helm upgrade --install openlens oci://ghcr.io/philippe-arnd/charts/openlens -n openlens --create-namespace
```

**Coolify:** point the service at `:0.7`. **systemd:** `curl … | sudo sh -s -- 0.7` ([guide](../deploy/systemd.md#install-in-one-command)). **OTLP behind a proxy:** allow 4 MB request bodies on `/v1/metrics`. The first start of v0.7.0 copies the data to `backups/upgrade/`.

## ⚠️ Changes in behaviour

- **The verdict is written back to GitHub, on by default** when the project has a GitHub repository and token for tickets (D-096). For production releases recorded with a commit range, once the verdict is *healthy* or *regressed* and within 7 days of the release, the hourly pass writes a commit status `openlens/release` on the deployed commit, a block in the GitHub release named like it, one comment on each shipped pull request (edited if the verdict changes, never repeated), and on a regression an issue with the evidence. Inconclusive verdicts are never written. It needs a fine-grained token with *Commit statuses*, *Contents*, *Issues* and *Pull requests* read and write (plus *Metadata* read), or a classic token with `repo`. **To keep OpenLens from writing**, give it a token without these write permissions: GitHub refuses, and the Releases page and `release_report` only show the refusal (#575).
- **The sidebar follows the method** (#621): Focus board, Ask, Releases, Live, Quality, Behaviour, People, Product, Settings, on access keys 1 to 9. Releases and Timeline have their own section, Goals moved to Product, Revenue is a People tab. Every page keeps its URL.
- **The Focus board changed layout.** Key numbers are now Outcomes tiles; Stickiness, average session and objectives at risk left the board (objectives stay on Goals and in the digest). Web Vitals, the releases table, paths to value, funnels and journeys, flag cohorts, role gaps and revenue moved to their pages: Pages, Releases, Behaviour › Feature flow, each feature's Overview, Flags, the Feature map and Revenue (#614–#620).
- **Recordings kept a day can grow with the disk** (#606). By default the disk budget is 80 % of the data volume minus what other files use, so a large disk now fills with more recordings. Set `OPENLENS_DISK_BUDGET` (a share or a size) to keep it smaller. Retention does not change: 400 days of events, 30 days of recordings.
- **The route-stats window can be 5 or 1 minutes** when the disk allows it (#628). The Node SDK follows the server's `x-openlens-stats-window` header; `statsWindowSeconds` pins it.
- **The change failure rate can go up**: it now counts releases judged regressed, as `docs/kpis.md` always said (#611).
- **Server events count in no user number** (#624). On a project that identifies nobody, server errors were counted as one more active user.

The data on disk is compatible, and nothing needs to be migrated by hand.

## 🧭 Known limitations

- **One node:** a single process with local disk.
- **Server SDKs:** route stats, slowest requests, dependencies and runtime health come from the Node SDK; other languages send route and dependency histograms through OpenTelemetry (`/v1/metrics`). OTLP is read for those two metrics only: no traces, no logs.
- **Write-back:** a release recorded without a commit range (often the project's first) gets no notes and is not written back, and `openlens-cli verify` does not check the token's write permissions yet.
- **Heatmap:** no Mobile / Tablet / Desktop split yet (one median width is kept per page), and labels and scroll depth cover the 15 most viewed pages.
- **Beta:** 0.x releases may change behaviour, always announced ([docs/stability.md](../stability.md)).
